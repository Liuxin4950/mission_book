# Mission Book — 领域模型

> 本文档定义 Mission Book 世界里存在哪些概念、每个概念负责什么、它们之间是什么关系，以及一个 Mission 从产生到结束的完整业务行为。
>
> 它是**术语的唯一来源**——其他文档在提到这些概念时必须使用这里的名字和含义。
>
> 本文档描述领域，不描述实现：不写 UI、不写数据库、不写 Flutter 类结构、不写 Agent。
>
> 每个概念带一个范围标记：
>
> - 【本版实现】— 当前这一版要做
> - 【本版只读】— 这一版会展示，但不产生新数据
> - 【本版不实现】— 只作为领域语言保留，落地见 [未来方向](未来方向.md)

---

# 1. 核心领域链路

```text
Goal            我要去哪？
   ↓
GoalNode        去那里大概要学 / 做些什么？
   ↓
Plan            按照我现在的状态，这一阶段怎么走？      【本版不实现】
   ↓
Mission         现在具体要执行什么？
   │
   ├── ExecutionPlan      这个 Mission 准备怎么执行？
   └── ExecutionHistory   这个 Mission 实际是怎么执行的？
   ↓
Evidence        你怎么知道我真的做了？
   ↓
Evaluation      做完以后，这说明我现在到了什么程度？    【本版不实现】
   ↓
Progress        我相对于 Goal 推进到了哪里？            【本版不实现】
   ↓
Replanning      根据真实结果，下一步应该怎么调整？      【本版不实现】
```

当前最重要的概念区别：

```text
Goal              长期方向
GoalNode          实现 Goal 需要经过的大纲节点
Plan              根据当前真实状态，这一阶段准备怎么走
Mission           当前真正要执行的一次行动
ExecutionPlan     这个 Mission 原本准备怎么执行
ExecutionHistory  这个 Mission 实际是怎么执行的
Evidence          行动留下的证据和结果材料
Evaluation        AI 根据执行过程与证据作出的判断
Replanning        根据真实结果重新调整后续计划
```

# 2. Goal【本版实现】

## 它回答的问题

> 我要去哪？

Goal 表示用户希望长期达到的方向、能力、结果或状态。

```text
学会 Flutter
完成 Mission Book
建立稳定运动习惯
```

Goal 不应该只是一个能够马上完成的小任务。`今天学习 Flutter 60 分钟` 更适合作为 Mission。

Goal 应该描述一个具有持续意义的方向。

## 状态

```text
ACTIVE     正在推进
PAUSED     暂时暂停，但没有放弃
ACHIEVED   目标已经达到
DROPPED    用户决定不再继续
```

## Goal 不保存什么

```text
今天几点学习 / 今天执行多久 / Mission Pause / Evidence / 具体 ExecutionPlan
```

这些属于更下面的领域。

---

# 3. GoalNode【本版实现】

## 它回答的问题

> 去那里大概要学 / 做些什么？

GoalNode 是 Goal 下面的大纲节点，可以继续包含 GoalNode，形成 Tree。

```text
Goal
学会 Flutter
   ↓
GoalNode Tree
Flutter
├── Dart
├── Widget
├── Layout
├── Navigation
│   ├── Navigator
│   ├── Route
│   └── Route Stack
├── State
├── Network
├── Persistence
└── Project Practice
```

GoalNode 最重要的作用不是制作一张永远不能修改的固定课程表，而是：

> **给长期 Goal 保留一个持续存在的大纲。**

这样可以降低：AI 长期运行后的遗忘、上下文漂移、只关注近期任务而忘记整体方向、更换模型后丢失整体结构、动态规划过程中逐渐偏离最初目标。

原则：

> **大纲可以修改，但不能没有大纲。**

## GoalNode 不保存进度

不要设计 `GoalNode.mastery = 82` 并把它当作事实。

GoalNode 描述"大纲是什么"；用户走到了哪里由 Mission 的完成情况推出（见 §10），未来由 Progress 表达。

---

# 4. Plan【本版不实现】

## 它回答的问题

> 按照我现在的状态，这一阶段怎么走？

Plan 不是 Goal，也不是某一个 Mission 的执行步骤。它表示根据用户当前真实状态，为实现某个 Goal 或推进某个阶段而制定的整体行动策略。

```text
Goal
学会 Flutter
   ↓
当前阶段 Plan
1. Route / Navigator 收尾
2. 开始 State 基础
3. 用 State 做 Mission Book 的第一个交互页面
4. 根据项目开发中暴露的问题继续调整学习路线
```

Plan 可以综合考虑：当前进度、用户可用时间、近期执行表现、当前 Context、Goal 优先级、过去的 Plan History、Mission Evaluation、实际执行历史。

## Plan 可以有归属，也可以独立存在

Plan 可以属于某个 Goal，也可以没有长期 Goal（考试周计划、身体恢复计划、旅行计划、本周临时安排）。因此 Plan 是一个独立领域概念。

## Plan 可以变化，但变化要留痕

Plan 是可调整的策略，不是不可修改的合同。但调整不应该覆盖旧计划——旧计划为什么存在，本身就是重要数据。

## 为什么这一版不实现

当前没有 AI Planner，也没有 Plan 编辑器，没有任何入口能产生 Plan。为一个没有产生路径的概念建模，只会得到空表和长期不执行的代码。

这一版 Mission 的归属只到 GoalNode 为止。

# 5. Mission【本版实现】

## 它回答的问题

> 现在具体要执行什么？

Mission 是用户真正可以开始、执行、暂停、继续、延长、结束、提交 Evidence 的一次行动单位。

```text
Mission
理解 Flutter Route Stack
预计时间：45 分钟
目标：通过 A → B → C 页面跳转实验，
     理解 push / pop 对路由栈产生的影响。
```

## 归属关系

Mission 可以属于：

```text
Goal → GoalNode → Mission
```

也可以**不属于任何长期 Goal**。

现实生活中存在很多临时任务：拿快递、制作明天要交的 PPT、处理学校临时事务。Mission Book 不应该为了结构漂亮，强迫现实生活中的每一件事情都进入 Goal Tree。

用户以后打开 Mission 时，应该能够看到它位于整个 Goal Tree 中的位置：

```text
Flutter > Navigation > Route > Route Stack 验证 Mission
```

这样用户可以明确知道：我今天为什么在做这件事情？这件事情与长期 Goal 有什么关系？

## Mission 的血缘

一个 Mission 可能由另一个 Mission 的结果产生。例如：

```text
Mission A  学习 Navigator
   ↓ 发现 Route Stack 缺口
Mission B  Route Stack Recall
```

Mission B 应保存：

```text
sourceMissionId = Mission A
relationType    = RECALL
```

当前支持的 relationType：

```text
RETRY        重做
RECALL       隔一段时间后回忆
SUPPLEMENT   补充缺口
PRACTICE     练习
APPLICATION  真实应用
FOLLOW_UP    后续跟进
```

血缘关系是**可选**的。普通独立 Mission 不需要强行关联来源 Mission。

## Mission 的 Why

Mission 应保存"为什么当前会安排这个 Mission"：

```text
Mission  理解 Flutter State
Why      Navigation 已经基本完成，
         State 是进入真正交互式 Flutter 页面之前的重要基础。
```

Why 不应该只是创建 Mission 时临时解释一次然后被丢弃。未来回看 `2026-08-28 学习 State` 时，本身信息并不完整；如果同时保留"为什么当时安排 State"，未来 AI 才能重新判断：当时 Planner 的决策是否合理？

因此 Why 属于需要被长期保存的 Mission 信息。

# 6. ExecutionPlan【本版实现】

## 它回答的问题

> 这个 Mission 准备怎么执行？

ExecutionPlan 属于某一个具体 Mission。

它和上层的 Plan 不是同一个概念：

```text
Plan           这一阶段准备怎么走？   → 跨多个 Mission
ExecutionPlan  这一个 Mission 准备怎么做？
```

## 四个核心部分

```text
Why     为什么做？      ← 保存在 Mission.why，不重复保存
What    这次具体做什么？
How     建议怎么做？
Verify  准备如何验证？
```

这些英文名称用于 Dart 模型、AI、Prompt、数据结构之间的统一概念。实际 UI 和说明仍然使用中文。

## ExecutionPlan 是计划，不是事实

它不代表用户最后一定会完全按照它行动。真实发生的过程由 ExecutionHistory 记录。

两者之间的差异本身就是非常重要的数据——未来 AI 可以不断比较 `Plan VS Reality`，从而逐渐改善规划能力。

## 修改规则

```text
Mission START 前  → 可以修改 ExecutionPlan
Mission START 后  → ExecutionPlan 锁定
```

因为开始以后再覆盖"原本准备怎么做"，会破坏 `Plan VS Reality` 的对比基础。

未来如果确实需要"执行途中修改方案"，再引入 ExecutionPlanRevision。**当前不做。**

---

# 7. ExecutionHistory【本版实现】

## 它回答的问题

> 这个 Mission 实际是怎么执行的？

Mission Book 不应该只保存 `Mission = Completed`，那样会丢失大量真实执行信息。

## Execution Event

当前保留五种核心事件：

```text
START  开始
PAUSE  暂停
RESUME 恢复
EXTEND 延长
END    结束
```

```text
14:20 START
14:50 PAUSE
15:10 RESUME
15:20 EXTEND +30min
15:50 END
```

这些事件组成 Mission 的真实执行时间线。

## 为什么用事件而不是时间字段

一种更简单的设计是在 Mission 中直接保存 `actualStart / actualEnd / pauseStart / pauseEnd / extensionStart / extensionEnd`。

但现实中可能出现"暂停 3 次、延长 2 次"，全部塞进 Mission 会很快变得混乱，而且丢失顺序。

因此：

```text
Mission
└── ExecutionHistory
    ├── START
    ├── PAUSE
    ├── RESUME
    ├── EXTEND
    └── END
```

## 事件的合法性

```text
合法：START → END
合法：START → PAUSE → RESUME → END
合法：START → PAUSE → RESUME → EXTEND → EXTEND → END

非法：PAUSE           （没有 START）
非法：START → RESUME  （没有 PAUSE）
非法：END → PAUSE     （Execution 已结束）
```

一个 Mission 最多 1 个 START、1 个 END。需要重新尝试时，创建新的 Retry Mission，**不要复活已经结束的旧 Mission**。

## Evidence 与 ExecutionHistory 的区别

```text
ExecutionHistory = 行动过程（什么时候开始、暂停、恢复、延长、结束）
Evidence         = 行动结果与证明材料（代码、截图、Commit、解释）
```

两者不能混为一谈。

# 8. Evidence【本版实现】

## 它回答的问题

> 你怎么知道我真的做了？

Evidence 是用户真实行动产生的证明材料或结果信息。

一个 Mission 可以拥有多个 Evidence：

```text
Mission  理解 Flutter Navigator
   ↓
Evidence
├── Code
├── Screenshot
├── Git Commit
└── User Explanation
```

## Evidence Draft 与 Formal Evidence

用户可能需要依次添加代码、截图和文字解释，因此第一次添加材料不代表 Evidence 已经正式提交。

```text
Finalize 前 = Evidence Draft
  = 应用层 / 表单暂存状态
  = 可以新增、删除、替换、修改
  = 不属于正式 Raw History

Finalize 后 = Formal Evidence
  = 进入正式 Raw History
  = 原则上追加保存
```

Evidence Draft **不作为核心领域对象**。它是表单状态，不是数据模型的一部分。

## Evidence 不保存评价

禁止：

```text
Evidence.valid = false
Evidence.score = 72
Evidence.mastery = basic
```

这些属于 Evaluation。Evidence 自己只描述：这是什么事实材料。

## Evidence 修正

如果需要修正已经 Finalize 的 Formal Evidence，不要直接覆盖历史，而是新增一条 Evidence 并指向被修正项（`supersedesEvidenceId`）。

# 9. Evaluation【本版不实现】

## 它回答的问题

> 做完以后，这说明我现在到了什么程度？

Evaluation 是 AI 基于 Mission + ExecutionHistory + Evidence 对本次结果作出的分析和判断。它属于 Derived Data。

## 为什么这一版不实现

当前没有接入真实 AI。这一版不会产生任何 Evaluation 数据，也不会生成任何模拟评价——**伪造的评价会污染 Memory，比没有评价更糟**。

Mission 走到等待评价的位置时会明确停住，UI 显示"智能评价暂未接入"。

## 领域原则（未来实现时必须遵守）

```text
一个 Mission 可以有多个 Evaluation，新的不覆盖旧的
Mastered 不能通过一次优秀表现获得
Score 是仪表盘，不是判决书
Execution / Verification / Mastery 不应压缩成一个 Done
Overall Score 不独自决定 Planner
```

具体设计见 [未来方向](未来方向.md)。

# 10. Mission 的进度口径【本版实现】

这一版没有 ProgressState，但 UI 需要展示 Goal 与 GoalNode 的推进情况。口径如下：

```text
节点已完成
  = 该节点存在 Mission，且该 Mission.userReportedResult = COMPLETED 并已关闭

节点正在学习
  = 该节点存在尚未关闭的 Mission

节点总数 / 完成数
  = 包含子节点的递归统计

Goal 进度
  = 已完成节点数 / 当前活动节点总数
```

这是**"关联 Mission 的完成执行覆盖"**，不是知识掌握度，也不是 AI Evaluation。

UI 上不得使用带掌握度含义的措辞（不写"已掌握""熟练"），只能表达"有完成记录""正在学习""还没有记录"。

# 11. Mission 生命周期

## 11.1 总览

```text
Mission Created
      ↓
（AI 生成时）Proposed → User Confirm      ← 本版不可达，见 §11.2
      ↓
Scheduled
      ↓
Ready
      ↓
Executing
      ├── Pause
      ├── Resume
      ├── Extend
      └── User End
      ↓
Execution End
      │
      ├── 用户标记未完成 → Not Completed → Failure Diagnosis
      │
      └── 用户表示已完成
               │
               ├── SELF_REPORT        → Closed
               ├── OPTIONAL_EVIDENCE  ├── 直接关闭 → Closed
               │                      └── 选择提交 → Evidence Pending
               └── REQUIRED_EVIDENCE  → Evidence Pending
                                              ↓
                                        Add Evidence Draft × N
                                              ↓
                                        Finalize Submission
                                              ↓
                                        Evaluation Pending
                                              ↓
                                    本版：明确显示智能评价未接入
```

REQUIRED_EVIDENCE 到达 Deadline 仍未 Finalize 时：

```text
Execution      = Completed
verificationState = MISSING_DEADLINE
lifecycleStage = CLOSED
closureReason  = EVIDENCE_DEADLINE_MISSED
```

它表示"已执行，但未完成验证闭环"，**不会把执行事实改写为"用户没有完成执行"**。

## 11.2 关于 Proposed / Confirmed

领域上，AI 生成的 Mission 应该先进入 Proposed，由用户接受、修改或拒绝后才进入计划。

本版没有 AI，所有 Mission 由用户手动创建——用户填写表单并保存，本身就是确认行为。因此 **PROPOSED 与 CONFIRMED 这两个状态在本版不可达**，实现时不应把它们做成占位状态。

## 11.3 时间类型

```text
FIXED      应尽可能在指定时间发生（会议、考试、预约）
PREFERRED  最好在某个时间执行，但允许调整（18:00 跑步）
FLEXIBLE   只需要在一定时间范围内执行，具体开始时间不重要
```

**本版只实现 FIXED 与 FLEXIBLE。** PREFERRED 需要完整的开始/结束时段输入与后续调度规则，当前不开放。

## 11.4 到达开始时间不等于逾期

```text
Scheduled → Ready
```

而不是 `Scheduled → Overdue`。

> 时间到了，只代表 Mission 现在适合开始，不代表用户已经失败。

## 11.5 Ready 状态下的行为

Ready 表示已经进入适合执行的时间范围，但用户还没有正式开始。

可能的用户操作：开始 / 稍后 / 临时有事 / 今天无法执行。

Mission Book 不应该在用户没有响应第一次通知时立刻认为异常。

## 11.6 用户出现临时事件

收到通知后，用户可以告诉 AI：临时开会、需要外出、电脑不在、突然有其他事情、今天只有 30 分钟、身体状态变化。

这不应该直接被记录成 Mission Failure，而应该首先理解为 **Context Changed**：

```text
User Reports Context Change
   ↓
AI Analyze
   ↓
Replan Proposal
   ↓
User Confirm
   ↓
Delay / Resize / Reschedule / Replace
```

【本版】没有 AI 做这一步。用户可以直接改时间（产生新的 Schedule Revision）、取消 Mission，或者按实际情况执行并在结束时如实报告。

## 11.7 时间记录

Mission 执行过程中需要区分多种时间，详见 §12。

## 11.8 Pause

```text
Executing → Pause → Resume → Executing
```

Pause 不应该删除 Mission 的运行状态。

Pause 应作为一种执行历史事件存在。原因可选——用户只是喝水、上厕所、接电话时，不应该每次暂停都被要求填写原因。

## 11.9 到达 Planned Time

当 Focus Time 到达 Original Planned Duration 时，系统**不应该自动完成 Mission**，而应该主动询问用户：

> 本次 Mission 的计划时间已经到了。

可能选择：结束 / 继续。

## 11.10 Extension

用户选择继续时：

```text
Executing → Extended
```

开始记录 Extension。Extension 应该作为执行历史的一部分保存。

Mission 延长以后，不需要等待某个新的固定结束时间。用户可以随时选择完成或未完成。

## 11.11 用户可以直接选择未完成

Mission 执行结束时，用户不应该被迫必须提交 Evidence。用户可以直接选择"任务未完成"：

```text
今天确实没搞懂 / 时间不够 / 中途放弃 / 突然有事 / 不想继续
```

系统应该允许用户诚实结束 Mission。

## 11.12 Not Completed 之后

```text
Execution End → Not Completed → Failure Diagnosis
```

之后可以轻量询问原因（时间不足 / 任务太难 / 临时有事 / 状态不好 / 不想继续 / 其他），**不强制填写说明**。

**Not Completed 不应该直接 Move to Tomorrow。**

可能结果包括：`Delay / Split / Reduce / Add Prerequisite / Reschedule / Replace / Drop / Retry`。

【本版】Failure 记录会保存，诊断与决策由用户自己完成，AI 建议见 [未来方向](未来方向.md)。

## 11.13 区分"没执行"和"没验证"

```text
情况 A   Execution: Not Started    Evidence: None
情况 B   Execution: Completed      Evidence: Missing
         Verification: Missing Deadline    Lifecycle: Closed
```

这两种情况完全不同。第二种依然说明：**用户已经完成执行，但验证闭环没有完成。** 这对未来 Planner 很有价值，不能被压缩成同一件事。

# 12. 时间口径

Mission 执行过程中应区分多种时间。

```text
Planned Time        Planner 原本预计 Mission 应投入多少时间
Elapsed Time        从用户开始到最终结束之间，总共经过了多少现实时间
Paused Time         累计暂停时间
Focus Time          真正处于任务执行状态的时间 = Elapsed - Paused
Granted Extension   用户通过 EXTEND 选择的额外计划执行额度
Actual Overtime     实际 Focus Time 超出原计划时长的部分
```

例如：

```text
14:00 START
14:40 PAUSE
15:10 RESUME
16:00 END

Elapsed Time: 120 min
Paused Time:   30 min
Focus Time:    90 min
```

两种 Extension 相关时间**不能混淆**：

```text
Granted Extension = 所有 EXTEND Event 的 grantedDurationMinutes 总和

Actual Overtime   = max(Focus Time - Original Planned Duration, 0)
```

Actual Overtime 必须基于 Focus Time，而不是 Elapsed Time——**Pause 不能被计算成实际超时执行时间**。

Original Planned Duration 来自 START Event 所绑定 Schedule Revision 的 plannedDurationMinutes，也就是 Mission 开始时的有效 Schedule 版本，**不是历史上最早的计划时长**。

## 这些数据将来有什么用

```text
Mission 是否经常估时过短 / 哪类任务容易暂停
用户在哪些时间段执行效果更好 / 哪类学习内容更加困难
用户能够维持多久专注 / Planner 应该如何调整未来任务
```

---

# 13. VerificationPolicy【本版实现】

不同 Mission 需要不同强度的验证流程：

```text
SELF_REPORT        用户报告完成即可关闭
OPTIONAL_EVIDENCE  用户可以直接关闭，也可以选择提交 Evidence
REQUIRED_EVIDENCE  用户报告完成后必须进入 Evidence 流程，并受 Evidence Deadline 约束
```

例如"拿快递"不应被强制要求 Evidence；需要客观成果验证的学习或运动 Mission 可以使用 REQUIRED_EVIDENCE。

## 结果矩阵

| Policy | 用户报告完成后的结果 |
| --- | --- |
| SELF_REPORT | CLOSED + NOT_REQUIRED |
| OPTIONAL_EVIDENCE / 选择不提交 | CLOSED + NOT_REQUIRED |
| OPTIONAL_EVIDENCE / 选择提交 | EVIDENCE_PENDING + NOT_SUBMITTED |
| REQUIRED_EVIDENCE | EVIDENCE_PENDING + NOT_SUBMITTED |

只有 REQUIRED_EVIDENCE 受 Evidence Deadline 约束。

## Evidence Pending 的意义

它表示：用户已经结束本次执行并表示完成，且根据策略已选择或必须进入 Evidence 流程。

这样用户不需要在真实行动结束后立刻完成验证：

```text
刚跑完步 → 结束 Mission → 回家以后再上传运动截图
电脑任务做完 → 稍后整理 Commit / Screenshot
```

---

# 14. Evidence Deadline【本版实现】

Evidence Deadline **只适用于 REQUIRED_EVIDENCE**。

默认最晚提交时间：

```text
任务所属当天 24:00
```

使用明确时间可以避免未来时区、设备、跨平台产生歧义。跨午夜 Mission 的特殊规则当前不展开，等真实使用暴露需求以后再设计。

SELF_REPORT 和 OPTIONAL_EVIDENCE 不因为未提交 Evidence 触发 Deadline 失败。

## 超时后

```text
Evidence = Missing
   ↓
Evidence Timeout
   ↓
lifecycleStage  = CLOSED
```

同时保留三个独立事实：

```text
userReportedResult = COMPLETED
verificationState  = MISSING_DEADLINE
lifecycleStage     = CLOSED
closureReason      = EVIDENCE_DEADLINE_MISSED
```

UI / 产品语义显示为：

> 已执行，但未完成验证闭环。

**不得删除或改写此前的 Raw History，也不得把用户的完成报告改成未完成。**

# 15. 失败路径【本版实现（仅原始事实）】

Failure 是 Mission Book 的一级数据。不能只保存 `Mission = NOT_COMPLETED` 然后结束。

## 什么时候产生 FailureRecord

```text
用户主动选择 NOT_COMPLETED
或
Evidence Deadline 到达但 Required Evidence 未 Finalize
```

后一种表示**验证闭环失败，不表示用户没有执行**。

## 用户可选择的失败原因

```text
TIME_INSUFFICIENT       时间不足
TOO_DIFFICULT           任务太难
URGENT_EVENT            临时有事
BAD_STATE               状态不好
DO_NOT_WANT_CONTINUE    不想继续
ENVIRONMENT_PROBLEM     环境不允许
OTHER                   其他
```

原因可以为空。**不要强迫用户写作文。**

## AI 诊断属于未来

"任务估时过短""缺少前置知识""重复出现逃避"这类判断属于 AI Derived Data，不是用户原始事实。本版不产生这些判断，见 [未来方向](未来方向.md)。

# 16. 业务原子操作

一个用户操作如果会同时改变多个必须保持一致的数据，就应该作为**一个业务原子操作**。

| 操作 | 必须同时完成 |
| --- | --- |
| CreateMission | Mission + ExecutionPlan + ScheduleRevision 全部存在，或全部不存在 |
| StartMission | 追加 START Event（绑定 scheduleRevisionId）+ LifecycleStage → EXECUTING + ExecutionState → RUNNING |
| PauseMission | 追加 PAUSE Event + RUNNING → PAUSED |
| ResumeMission | 追加 RESUME Event + PAUSED → RUNNING |
| ExtendMission | 追加 EXTEND Event（记录额度），**不修改 Original Planned Duration** |
| EndMission (Completed) | 追加 END Event + ExecutionState → ENDED + UserReportedResult → COMPLETED + 按策略分流 |
| EndMission (Not Completed) | 追加 END Event + ExecutionState → ENDED + UserReportedResult → NOT_COMPLETED + CLOSED + 创建 FailureRecord |
| FinalizeEvidenceSubmission | 校验 Draft + 保存 Formal Evidence[] + VerificationState → SUBMITTED + LifecycleStage → EVALUATION_PENDING |
| ApplyEvidenceDeadline | VerificationState → MISSING_DEADLINE + CLOSED + closureReason + 创建 FailureRecord |
| RescheduleMission | 追加 ScheduleRevision + 记录 changeReason + REQUIRED_EVIDENCE 时同步重算 evidenceDeadlineAt |

反例：

```text
Mission 显示 Executing，却没有 START Event
有 START Event，Mission 却仍然显示 Ready
Mission 是 Not Completed，却没有 FailureRecord
```

## AI 调用不属于业务原子操作

如果未来接入 AI：

```text
正确：Evidence 保存成功 → 等待 Evaluation → AI Evaluation
错误：保存 Evidence + AI 请求 + Evaluation 必须同时成功
```

数据库 Transaction 是业务原子性的**实现手段**，不是业务规则本身。

# 17. 领域原则

## 17.1 Raw History 优先

真实发生过的事情优先保留，不能最后只剩一个最终状态。

## 17.2 原始事实与 AI 判断分离

```text
Raw Fact → Derived Evaluation
```

而不是：

```text
AI Evaluation → 修改 Raw Fact
```

## 17.3 能算出来的不重复存

`START / PAUSE / RESUME / END` 已经能够算出 Elapsed / Paused / Focus，这些统计值不应该和 ExecutionEvent 同时成为两套互相独立的事实。

ExecutionEvent 才是 Source of Truth。统计值可以实时计算，未来为了性能也可以缓存，**但缓存损坏以后必须能重新算出来**。

## 17.4 修改不能抹掉历史

需要修改时优先追加新版本，而不是覆盖旧版本。

## 17.5 领域层优先表达真实业务含义

而不是优先满足"数据库方便、代码少、字段少、实现简单"。

例如 Mission 的执行过程真实存在 START / PAUSE / RESUME / EXTEND / END，领域层就应该首先承认这些概念存在——至于最终数据库如何高效保存，是后面的技术问题。

## 17.6 AI 是智能层，不是领域本身

Goal、GoalNode、Plan、Mission、ExecutionPlan、ExecutionHistory、Evidence、Evaluation 这些概念，即使未来模型从 OpenAI 换到 Claude 再换到本地模型，也依然应该存在。
