# Mission Book — 数据模型

> 本文档定义当前这一版**最少需要保存哪些数据**、它们之间的关系，以及哪些字段是 Source of Truth。
>
> 它不是数据库设计：不写 SQL、不写 Dart Class、不写 Repository 实现。字段名用于表达语义，实现时可以调整命名，但语义不能改。
>
> **原则：本文档只建模这一版真实存在的东西。** 没有产生路径的对象、字段、枚举，一律不进模型——它们放在 [未来方向](未来方向.md)，等有实现路径时再升级。
>
> 与 [领域模型](领域模型.md) 冲突时，以领域模型为准。

---

# 1. 设计原则

## 1.1 Raw Fact 优先

真实发生过的事情优先保留。

```text
14:03 START / 14:42 PAUSE / 14:55 RESUME / 15:20 END
```

不能最后只剩 `Mission = Completed`。

## 1.2 原始事实与 AI 判断分离

```text
Raw Fact → Derived Evaluation
```

不是：

```text
AI Evaluation → 修改 Raw Fact
```

## 1.3 能计算出来的数据尽量不重复成为真相来源

ExecutionEvent 是 Source of Truth，Elapsed / Paused / Focus 都是算出来的。统计值可以缓存，但缓存损坏后必须能重建。

## 1.4 修改不能轻易抹掉历史

Schedule 变更靠追加 Revision，而不是覆盖。

## 1.5 一个业务动作必须保持内部一致

不能只有 START Event 而 Mission 仍是 Ready，也不能 Mission 是 Executing 而没有 START Event。见 [领域模型 §16](领域模型.md)。

## 1.6 当前不建模的东西

```text
Plan / PlanRevision / PlanStep   没有创建入口
Evaluation / Scores / Mastery    没有 AI，产生不了
ContextState / ProgressState     当前不实现
Reflection / Derived Memory      当前不实现
```

这些不是"先留字段以后用"，而是**不写入模型**。理由见 [产品纲领 §13](产品纲领.md) 与 [本地应用规格](本地应用规格.md)。

# 2. 数据对象总览

```text
目标层
├── Goal
└── GoalNode

Mission 层
├── Mission
├── MissionScheduleRevision   (Mission 下的版本化值对象)
├── ExecutionPlan
└── ExecutionEvent

验证层
└── Evidence

失败层
└── FailureRecord

非对象
└── Evidence Draft            (应用层表单状态，不是数据模型的一部分)
```

关系：

```text
Goal 1 ──── * GoalNode
  │              │
  └──────┬───────┘
         ↓
      Mission 1 ──── 1 ExecutionPlan
         │
         ├── * MissionScheduleRevision
         ├── * ExecutionEvent
         ├── * Evidence
         └── * FailureRecord
```

Mission 的 Goal / GoalNode 归属是**可选**的。

# 3. Goal

## 3.1 代表什么

用户长期想达到哪里。

```text
学会 Flutter
完成 Mission Book
建立稳定运动习惯
```

## 3.2 字段

| 字段 | 含义 | 必须 |
| --- | --- | --- |
| id | Goal 唯一身份 | 是 |
| title | Goal 名称 | 是 |
| description | 更完整的描述 | 否 |
| why | 用户为什么希望实现这个 Goal | 否 |
| status | 当前状态 | 是 |
| createdBy | USER / AI / SYSTEM | 是 |
| createdAt | 创建时间 | 是 |
| updatedAt | 最近修改时间 | 是 |

## 3.3 Goal Status

```text
ACTIVE     正在推进
PAUSED     暂时暂停，但没有放弃
ACHIEVED   目标已经达到
DROPPED    用户决定不再继续
```

## 3.4 Goal 不保存

```text
今天几点学习 / 今天执行多久 / Mission Pause / Evidence / 具体 ExecutionPlan
```

# 4. GoalNode

## 4.1 代表什么

实现 Goal 过程中需要经过的大纲节点，通过 `parentNodeId` 形成 Tree。

## 4.2 字段

| 字段 | 含义 | 必须 |
| --- | --- | --- |
| id | 节点唯一身份 | 是 |
| goalId | 所属 Goal | 是 |
| parentNodeId | 父节点 | 否（为空即根节点） |
| title | 节点名称 | 是 |
| description | 节点说明 | 否 |
| orderIndex | 同级排序 | 是 |
| status | 节点是否仍然有效 | 是 |
| createdAt | 创建时间 | 是 |
| updatedAt | 修改时间 | 是 |

## 4.3 进度不在 GoalNode 上

不要保存 `GoalNode.mastery`。节点的完成情况由关联 Mission 推出，口径见 [领域模型 §10](领域模型.md)。

# 5. Mission

## 5.1 代表什么

用户真正能够开始并执行的一次行动。

## 5.2 Mission 不负责什么

```text
所有 Pause / 所有 Resume / 所有 Evidence 内容 / 完整 Evaluation / 所有 Plan 历史
```

这些都有自己的数据对象。Mission 是这些数据之间的**连接点**。

## 5.3 字段

### Identity

| 字段 | 含义 | 必须 |
| --- | --- | --- |
| id | Mission 唯一身份 | 是 |
| title | Mission 名称 | 是 |
| description | 更详细说明 | 否 |
| why | 为什么当前安排它 | 条件必须 |
| createdBy | USER / AI / SYSTEM | 是 |

`why` 对 AI 生成的 Mission 必须存在；用户临时创建的（如"拿快递"）可以没有。

### Belonging

| 字段 | 含义 | 必须 |
| --- | --- | --- |
| goalId | 所属 Goal | 否 |
| goalNodeId | 所属 GoalNode | 否 |

### Lineage

| 字段 | 含义 | 必须 |
| --- | --- | --- |
| sourceMissionId | 来源 Mission | 否 |
| relationType | 与来源 Mission 的关系 | 否 |

`relationType` 取值：`RETRY / RECALL / SUPPLEMENT / PRACTICE / APPLICATION / FOLLOW_UP`。

### Schedule

| 字段 | 含义 | 必须 |
| --- | --- | --- |
| scheduleRevisions | 时间安排版本列表 | 是（至少一条） |
| evidenceDeadlineAt | 最晚 Evidence 提交时间 | 条件必须 |

`evidenceDeadlineAt` 只在 `verificationPolicy = REQUIRED_EVIDENCE` 时必须。

### State

| 字段 | 含义 | 必须 |
| --- | --- | --- |
| lifecycleStage | 流程走到哪一步 | 是 |
| executionState | 真实执行状态 | 是 |
| userReportedResult | 用户自己的完成报告 | 是 |
| verificationPolicy | 采用哪种验证策略 | 是 |
| verificationState | 验证流程进行到哪 | 是 |
| closureReason | 关闭原因 | 否 |

### Audit

| 字段 | 含义 |
| --- | --- |
| createdAt / updatedAt | 创建与修改时间 |
| readyAt | 进入 READY 的时间 |
| closedAt | 关闭时间 |

## 5.4 完整结构

```text
Mission
├── Identity   id / title / description? / why? / createdBy
├── Belonging  goalId? / goalNodeId?
├── Lineage    sourceMissionId? / relationType?
├── Schedule   scheduleRevisions[] / evidenceDeadlineAt?
├── State      lifecycleStage / executionState / userReportedResult
│              / verificationPolicy / verificationState / closureReason?
├── Reference  executionPlanId?
└── Audit      createdAt / updatedAt / readyAt? / closedAt?
```

# 6. Mission 的状态不能只有一个 status

禁止设计 `status = COMPLETED`，然后让一个字段同时承担生命周期、执行状态、Evidence 状态、验证结果——那会产生一个几十个枚举值的怪物。

Mission 拆成四个独立维度。

## 6.1 LifecycleStage

> Mission 当前流程走到哪里？

```text
SCHEDULED           已经安排好时间
READY               现在已经适合开始
EXECUTING           用户已经开始执行
EVIDENCE_PENDING    执行结束，等待 Evidence Finalize
EVALUATION_PENDING  Formal Evidence 已保存，等待评价
CLOSED              生命周期结束
CANCELLED           Mission 被用户取消（不是失败，而是这个 Mission 不再需要执行）
```

`PROPOSED / CONFIRMED` 属于未来 AI 生成路径，本版不可达，**不实现**。

## 6.2 ExecutionState

> 用户现在的真实执行状态是什么？

```text
NOT_STARTED
RUNNING
PAUSED
ENDED
```

**Source of Truth 是 ExecutionEvent[]。** 本字段是为了 UI 查询而缓存的投影；如果与事件不一致，以事件重建。

## 6.3 UserReportedResult

用户结束 Mission 时的自我报告：

```text
PENDING
COMPLETED
NOT_COMPLETED
```

这是**用户自己的事实性报告**，不是 AI Evaluation。

## 6.4 VerificationState

> Evidence / 验证流程目前进行到哪里？

```text
NOT_REQUIRED       根据策略不需要进入 Evidence 流程，或用户选择不提交
NOT_SUBMITTED      已进入 Evidence 流程，尚未提交
SUBMITTED          Formal Evidence 已保存
MISSING_DEADLINE   REQUIRED_EVIDENCE 超时未提交
```

它**只描述流程状态，不表达 AI 判断结果**。`Verified / Partial / Failed` 属于 Evaluation，本版不产生。

## 6.5 closureReason

可选审计字段，只解释 Mission 为什么关闭，不评价目标是否达成。

当前使用：

```text
EVIDENCE_DEADLINE_MISSED     Required Evidence 超时
EVALUATION_NOT_AVAILABLE     已提交 Evidence，但当前没有 AI 可以评价（本版主要出口）
```

## 6.6 Mission 如何关闭

不使用 `CompletionResult`，也不新增 `MissionOutcome`。Mission 如何关闭由独立事实共同表达：

```text
LifecycleStage + UserReportedResult + VerificationState + closureReason?
```

例如 Required Evidence 超时：

```text
userReportedResult = COMPLETED
verificationState  = MISSING_DEADLINE
lifecycleStage     = CLOSED
closureReason      = EVIDENCE_DEADLINE_MISSED
```

它表示"已执行，但未完成验证闭环"。

**不得把 userReportedResult 改写为 NOT_COMPLETED。**

# 7. MissionScheduleRevision

## 7.1 为什么需要

Mission 的时间安排可能变化：

```text
原计划 14:00 → 临时有事 → 改成 17:00
```

不能只覆盖 `14:00 → 17:00`，否则未来 AI 不知道"原来为什么没有在 14:00 开始"。

## 7.2 字段

```text
id
revisionNumber
scheduledDate
timePolicy              FIXED / FLEXIBLE（本版只这两种）
fixedStartAt?           timePolicy = FIXED 时必须
plannedDurationMinutes
timeZone
changeReason?
changedBy
changedAt
```

当前 Schedule 就是"最新的有效 Revision"，不另立第二套真相。

本版不实现 `windowStartAt / windowEndAt`（属于 PREFERRED 策略）。

# 8. ExecutionPlan

## 8.1 字段

| 字段 | 含义 | 必须 |
| --- | --- | --- |
| id | 唯一身份 | 是 |
| missionId | 所属 Mission | 是 |
| objective | What，这次具体要达到什么 | 是 |
| steps | How，推荐执行步骤（有序列表） | 否 |
| verificationCriteria | Verify，准备如何验证 | 是 |
| notes | 补充说明 | 否 |
| createdBy | USER / AI | 是 |
| createdAt / updatedAt | 时间 | 是 |

## 8.2 Why 不在这里

`Why` 正式保存在 `Mission.why`，ExecutionPlan 不保存第二份。

UI 可以组合展示：

```text
Mission.why + ExecutionPlan.objective + ExecutionPlan.steps + ExecutionPlan.verificationCriteria
=
Why / What / How / Verify
```

## 8.3 修改规则

```text
START 前 → 可以修改
START 后 → 锁定
```

未来如果确实需要"执行途中修改方案"，再引入 ExecutionPlanRevision。当前不做。

# 9. ExecutionEvent

Mission 实际执行历史的 **Source of Truth**。

## 9.1 字段

| 字段 | 含义 | 必须 |
| --- | --- | --- |
| id | Event 唯一身份 | 是 |
| missionId | 所属 Mission | 是 |
| type | START / PAUSE / RESUME / EXTEND / END | 是 |
| occurredAt | 实际发生时间 | 是 |
| scheduleRevisionId | START 时使用的 Schedule 版本 | 条件（仅 START） |
| grantedDurationMinutes | EXTEND 获得的额外计划执行额度 | 条件（仅 EXTEND） |
| reason | 原因 | 否 |
| userReportedResult | END 时用户报告结果 | 条件（仅 END） |
| createdBy | USER / SYSTEM | 是 |

## 9.2 START 为什么绑定 scheduleRevisionId

为了永远知道：**用户开始执行的时候，系统认为的计划到底是哪一个版本。**

这也是计算 Original Planned Duration 的依据。

## 9.3 EXTEND 的语义

```text
Planned: 60 min
EXTEND:  30 min
```

这里的 30 分钟表示 **Granted Extension**，不代表用户实际额外投入了 30 分钟。

**绝对不要修改 `plannedDuration`**（60 → 90），否则原计划被污染。

## 9.4 END

需要记录 `occurredAt` 与 `userReportedResult`。

## 9.5 统计口径

```text
Actual Start            = 第一次 START
Actual End              = END
Elapsed Time            = END - START
Paused Time             = 所有 PAUSE → RESUME / END 区间之和
Focus Time              = Elapsed Time - Paused Time
Granted Extension       = 所有 EXTEND 的 grantedDurationMinutes 之和
Original Planned Duration = START 绑定的 ScheduleRevision.plannedDurationMinutes
Actual Overtime         = max(Focus Time - Original Planned Duration, 0)
```

Actual Overtime 必须基于 Focus Time，而不是 Elapsed Time。

# 10. Evidence

## 10.1 代表什么

用户真实行动留下的材料。这里的 Evidence 专指 **Finalize 后的 Formal Evidence**，它是 Raw Fact。

Finalize 前的 Evidence Draft 是应用层 / 表单暂存状态，**不是数据模型的一部分**，也不进入 Raw History。

## 10.2 字段

| 字段 | 含义 | 必须 |
| --- | --- | --- |
| id | Evidence 唯一身份 | 是 |
| missionId | 所属 Mission | 是 |
| type | Evidence 类型 | 是 |
| source | 来源 | 是 |
| payload | 实际内容或引用 | 是 |
| capturedAt | 实际产生时间 | 否 |
| submittedAt | Finalize 成为 Formal Evidence 的时间 | 是 |
| createdBy | USER / SYSTEM | 是 |
| supersedesEvidenceId | 修正的是哪条旧 Evidence | 否 |
| metadata | Provider 附加信息 | 否 |

## 10.3 Type（本版实际支持）

```text
TEXT              文字说明
CODE              代码
IMAGE             图片 / 截图
FILE              文件
MANUAL_RECORD     手动记录
```

以下类型属于未来扩展，本版不实现、不写占位：

```text
VIDEO / GIT_COMMIT / REPOSITORY / HEALTH_DATA / APP_EXPORT / AI_QA / EXTERNAL
```

## 10.4 Source（本版实际支持）

```text
USER          用户直接输入
FILE_SYSTEM   从设备选择文件
CAMERA        拍照
```

以下属于未来扩展：`GIT / GITHUB / HEALTH_PROVIDER / EXTERNAL_APP / AI_INTERVIEW / MCP / SKILL`。

## 10.5 Payload

不同 Evidence 内容不同：

```text
TEXT / CODE      → 文本内容
IMAGE / FILE     → 应用私有目录下的相对 storageKey
MANUAL_RECORD    → 文本内容
```

具体 Dart 表示（sealed class / union）由实现决定。核心约束是：**数据库不保存来源文件的绝对路径**，只保存应用私有目录下的相对键。

## 10.6 Evidence 不保存评价

```text
Evidence.valid / Evidence.score / Evidence.mastery
```

全部禁止。这些属于 Evaluation。

# 11. FailureRecord

## 11.1 什么时候产生

```text
用户主动选择 NOT_COMPLETED
或
Evidence Deadline 到达但 Required Evidence 未 Finalize
```

后一种表示验证闭环失败，不表示用户没有执行。

## 11.2 字段（本版只保存原始事实）

```text
id
missionId
trigger                  USER_MARKED_NOT_COMPLETED / EVIDENCE_DEADLINE_MISSED
occurredAt
userReasonCategory?      TIME_INSUFFICIENT / TOO_DIFFICULT / URGENT_EVENT
                         / BAD_STATE / DO_NOT_WANT_CONTINUE
                         / ENVIRONMENT_PROBLEM / OTHER
userReasonText?          用户补充说明，可选
createdAt
```

原因可以为空。**不要强迫用户写作文。**

## 11.3 本版不保存 AI 诊断

`diagnosisSummary / factors / confidence / recommendedDecision / resultingPlanRevisionId` 等字段属于 AI Derived Data，本版没有 AI 产生它们，**不写入模型**。

# 12. 数据分类

## Raw Fact — 追加，不覆盖

```text
ExecutionEvent
Evidence（Formal）
UserReportedResult
FailureRecord 的原始原因
用户确认 / 拒绝行为
```

## Versioned Business Data — 修改时保存历史

```text
MissionScheduleRevision
```

## Editable Business Data — 允许正常修改

```text
Goal / GoalNode / Mission Metadata
ExecutionPlan（START 前）
```

## Derived Data — 允许重新计算

```text
Elapsed / Paused / Focus / Granted Extension / Actual Overtime
```

## 不属于数据模型

```text
Evidence Draft（表单状态）
```

# 13. 一致性约束

```text
Rule 1   Mission 不允许 EXECUTING 却没有 START Event
Rule 2   一个 Mission 最多 1 个 START、1 个 END；重试要创建新 Mission
Rule 3   不能 PAUSE 一个 NOT_STARTED 的 Mission
Rule 4   不能 RESUME 一个 RUNNING 的 Mission
Rule 5   不能 EXTEND 一个 ENDED 的 Mission
Rule 6   END 后不能继续写 PAUSE / RESUME / EXTEND
Rule 7   ExecutionPlan 在 START 后不能被直接覆盖
Rule 8   GoalNode.parentNodeId 如果存在，必须属于同一个 Goal
Rule 9   Mission.goalNodeId 如果存在，必须属于 Mission.goalId 对应 Goal
Rule 10  Formal Evidence 必须属于一个 Mission
Rule 11  sourceMissionId 与 relationType 必须同时存在或同时为空
Rule 12  sourceMissionId 不能指向 Mission 自身
Rule 13  只有 OPTIONAL_EVIDENCE（用户选择提交）或 REQUIRED_EVIDENCE 可以进入 EVIDENCE_PENDING
Rule 14  SELF_REPORT 与选择不提交的 OPTIONAL_EVIDENCE 必须关闭为 verificationState = NOT_REQUIRED
Rule 15  evidenceDeadlineAt 只对 REQUIRED_EVIDENCE 条件必填
Rule 16  Required Evidence 超时必须同时满足：
         userReportedResult = COMPLETED
         verificationState  = MISSING_DEADLINE
         lifecycleStage     = CLOSED
         closureReason      = EVIDENCE_DEADLINE_MISSED
Rule 17  Evidence Draft 不是数据模型的一部分；只有 Finalize 才创建 Formal Evidence
Rule 18  grantedDurationMinutes 只表示额外计划执行额度，不得用它或 Elapsed Time 代替 Actual Overtime
Rule 19  任何 Mission 最多绑定一个 ExecutionPlan
```

# 14. Source of Truth

| 内容 | Source of Truth |
| --- | --- |
| Mission 身份 | Mission |
| Mission 血缘 | Mission.sourceMissionId + Mission.relationType |
| Goal Tree | Goal + GoalNode |
| Mission 当前 Schedule | 最新有效 MissionScheduleRevision |
| Mission 实际执行过程 | ExecutionEvent[] |
| Focus Time / Elapsed / Paused | 由 ExecutionEvent[] 计算 |
| Granted Extension | ExecutionEvent[type = EXTEND].grantedDurationMinutes |
| Formal Evidence | FinalizeEvidenceSubmission 产生的 Evidence[] |
| 验证流程 | Mission.verificationPolicy / verificationState / lifecycleStage / closureReason |
| 用户完成报告 | Mission.userReportedResult + END Event |
| 失败原始事实 | FailureRecord |

# 15. 一个完整 Mission 的数据关系示例

```text
Goal        学会 Flutter
   ↓
GoalNode    Navigation
   ↓
Mission     理解 Route Stack
            why = 进入 State 前完成 Navigation 收尾
            verificationPolicy = REQUIRED_EVIDENCE
   ↓
ScheduleRevision 1
            date = 2026-08-28
            policy = FLEXIBLE
            planned = 60 min
   ↓
ExecutionPlan
            objective = 理解 Route Stack
            steps = [A → B → C 页面实验]
            verificationCriteria = 代码 + 自己解释 push/pop
   ↓
ExecutionEvent
            14:20 START   (scheduleRevisionId = 1)
            14:50 PAUSE
            15:10 RESUME
            15:20 EXTEND  granted +30
            15:50 END     userReportedResult = COMPLETED
   ↓
Evidence Draft（表单内）
   ↓ FinalizeEvidenceSubmission
Formal Evidence  Code / Screenshot / User Explanation
   ↓
lifecycleStage = EVALUATION_PENDING
verificationState = SUBMITTED
   ↓
本版：明确显示「智能评价未接入」
用户确认后 → CLOSED，closureReason = EVALUATION_NOT_AVAILABLE
```

派生时间：

```text
Planned 60 min
Elapsed 90 min
Paused  20 min
Focus   70 min
Granted Extension 30 min
Actual Overtime   10 min
```

**注意不要粗暴地认为"用户做了 90 分钟"。**

# 16. 当前冻结结论

```text
Goal / GoalNode
Mission / MissionScheduleRevision / ExecutionPlan / ExecutionEvent
Evidence
FailureRecord（仅原始事实）

Raw Fact First
ExecutionEvent 是执行事实的唯一来源
Evidence Draft 与 Formal Evidence 的边界
Schedule Revision 而不是覆盖
多维 Mission 状态（Lifecycle / Execution / Verification / ClosureReason）
业务原子操作
用户拥有最终决定权
Granted Extension 与 Actual Overtime 分离
```

除此之外不增加新的核心数据对象。

除非实际开发过程中发现"当前模型无法表达一个真实业务场景"，否则优先实现，而不是继续扩展模型。
