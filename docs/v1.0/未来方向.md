# Mission Book — 未来方向

> 本文档收集**已经想过、但当前不实现**的能力。
>
> 它存在的意义是：把"以后要做"和"现在要做"分开，让 [数据模型](数据模型.md) 保持干净，同时不丢掉已经想清楚的设计。
>
> **硬规则：本文档中的任何内容，都不得以空表、占位接口、未使用字段、注释掉的代码的形式提前进入工程。** 只有真正开始实现时，才把对应内容提升为正式规格。

# 1. 什么时候把一条内容提升为正式规格

同时满足这三条才提升：

```text
1. 当前闭环已经稳定运行
2. 这一条解决的是真实使用中暴露的问题，不是想象中的问题
3. 它的数据来源已经存在（或随本条一起产生）
```

否则继续留在这里。

# 2. AI 层

## 2.1 Evaluation

AI 基于 Mission + ExecutionHistory + Evidence 对结果作出判断。

```text
Evaluation
├── verificationResult       VERIFIED / PARTIALLY_VERIFIED / FAILED / UNVERIFIED
├── outcomeResult            ACHIEVED / PARTIALLY_ACHIEVED / NOT_ACHIEVED / UNKNOWN
├── scores                   Completion / Understanding / Independence / Quality / Overall
├── masteryAssessment?       LEARNING / BASIC / PROFICIENT / MASTERED
├── findings                 主要发现
├── weakPoints?              薄弱点
├── nextActionRecommendation 下一步建议
├── assistanceSummary?       本次 AI 帮助情况
├── confidence?              AI 对判断的置信度
├── evaluator                哪个模型进行评价
└── supersedesEvaluationId?  替代的是哪次旧评价
```

关键规则：

- **一个 Mission 可以有多个 Evaluation**，新评价不覆盖旧评价。模型升级后可以重新分析同一批原始材料。
- `FAILED` 与 `UNVERIFIED` 必须区分：一个是"看得出来没有达到"，一个是"看不出来到底达没达到"。
- Evaluation 不能修改 Formal Evidence。
- **Score 是仪表盘，不是判决书。** Planner 应读取评分结构而非总分——Understanding 95 / Independence 55 与 Understanding 70 / Independence 90 即使 Overall 都是 80，下一步也应该完全不同。
- **Mastered 不能通过一次优秀表现获得**：

```text
Initial Learning → Time Gap → Recall → Real Application → Re-verification → Mastered
```

Mastery 最终应由多个 Mission 的 Evaluation 共同影响 Progress，而不是一个 Mission 自己决定。

- Mastery 是可选维度。跑步 5km 只需要考虑 Execution + Verification，不需要 Mastery。

## 2.2 Planner

Planner 不只是"帮用户生成 Todo"。它需要综合：

```text
Goal Tree + Goal Policy + Current Plan + Plan History + Mission History
+ Current Context + Available Time + User Preference
+ Evidence + Evaluation + Execution History
```

然后生成 Mission Proposal，再由用户确认后进入执行。

核心目标不是 Maximum Productivity，也不是 Maximum Task Completion，而是：

> Sustainable Human Growth——在真实生活可以长期承受的前提下，让用户持续获得真正属于自己的能力。

**Planner 的优化目标由 Goal 决定。** 不同 Goal 可以有不同风格：

```text
Stable    稳定完成 / 长期坚持 / 较低失败率
Balanced  稳定 + 挑战
Growth    更高挑战 / 更快成长 / 允许更多失败
```

## 2.3 Goal Policy

未来每个 Goal 可以拥有自己的策略：

```text
Goal
├── Direction
├── Priority
├── Time Horizon
├── Daily Time
├── Preferred Time
├── Default Load
├── Challenge Style
├── AI Assistance
├── Verification Style
└── Data Sources
```

例如"Flutter 学习"和"跑步"可以采用完全不同的 Planner 策略。

## 2.4 Failure Diagnosis 与 Decision

用户标记未完成后，AI 可以判断：

```text
任务估时过短 / 缺少前置知识 / 任务拆分过大
当前 Context 不适合 / 重复出现逃避 / Goal 优先级已经变化
```

可能建议：

```text
DELAY / SPLIT / REDUCE / REPLACE / ADD_PREREQUISITE / REPLAN / DROP / KEEP / RETRY
```

**AI 只提出建议，最终由用户确认。**

## 2.5 Assistance Ladder

AI 帮助强度可以分级：

```text
Level 0  引导——让用户继续独立思考
Level 1  提示——给出方向，但不直接回答
Level 2  关键知识——提供必须理解的核心概念
Level 3  示例 / 答案——直接给出关键答案，并解释原因
Level 4  完整教学——最小案例 / 对比实验 / 调用链 / 运行过程 / 反例 / 图示 / 类比 / 分步骤验证
```

**Assistance 本身也是学习数据。** 两个用户都完成了同一个任务，独立完成与"AI 给出完整答案后完成"不能认为 Mastery 相同。

值得记录：AI Assistance Level、尝试次数、独立程度、提示次数、是否需要完整答案。

```text
Day 1   Assistance Level 4
Day 5   Assistance Level 2
Day 10  Assistance Level 0
```

这种变化本身就是能力增长的重要证据。

## 2.6 Execution Assistant

当前不优先实现 AI 实时陪伴（模型成本、Token 成本、实现复杂度，且不是核心闭环的必要能力）。

当前执行原则：

```text
规划时 AI 多思考
执行时用户真正行动
```

未来可以预留 `Off / Minimal / On Demand / Active` 几档，也可以使用更弱、更便宜的模型处理执行陪伴。

## 2.7 通知的上下文能力

通知未来可以结合上下文：

```text
今天的核心 Mission 还没有开始。
最近数据显示，你上午学习 Flutter 的完成率更高。
今天剩余时间不够，我建议取消次要 Mission。
前几天你说身体状态不好，现在恢复得怎么样？
```

# 3. Plan 相关

## 3.1 Plan

表示"按照我现在的状态，这一阶段怎么走"，可以属于某个 Goal，也可以独立存在（考试周计划、身体恢复计划、旅行计划）。

Plan 是独立领域概念，当前没有创建入口，因此不建模。

## 3.2 PlanRevision

Plan 的修改不应该覆盖旧计划：

```text
Plan
├── Revision 1
├── Revision 2
└── Revision 3
```

```text
PROPOSED → ACTIVE     用户确认
PROPOSED → REJECTED   用户拒绝
ACTIVE   → SUPERSEDED 被新版本取代
```

一旦 ACTIVE 就不再修改内容，需要修改就产生新 Revision。这样 Plan History 永远存在。

## 3.3 PlanStep

PlanRevision 中的阶段步骤（Value Object，不是独立实体）：

```text
stepKey / order / title / description? / goalNodeId?
```

Mission 如果来自某个 PlanStep，可以保存 `planStepKey`，这样未来能知道"这个 Mission 当时属于 Plan 的哪一步"。

## 3.4 为什么 Mission 要同时保存 planId 与 planRevisionId

如果只保存 `planId`，而 Plan 已经到 Revision 5，未来 AI 可能误以为这个 Mission 是按照今天的计划产生的。保存 `planRevisionId` 表示"它出生时的规划背景"。

## 3.5 ExecutionPlanRevision

如果真实需求出现"执行途中修改方案"，再引入。当前 ExecutionPlan 在 START 后锁定。

# 4. Context State

Mission Book 不只需要知道"用户长期是什么样"，还需要知道"用户现在是什么状态"。

```text
id / type / summary / source / confidence
startedAt / expectedEndAt / reviewAt / endedAt
planningImpact / createdAt / updatedAt
```

生命周期：

```text
ACTIVE → REVIEW → 继续 ACTIVE
ACTIVE → ENDED
```

## 关键规则

- **Context State 不应该无限持续。** "今天状态不好"不能让 AI 半年后还认为用户状态不好——需要 `reviewAt`，到时间主动重新确认。
- **默认有效期不是事实。** 设置复查时间不是认为"用户一定 7 天恢复"，而是"7 天以后应该重新确认"。
- **推断必须谨慎。** 用户明确说的（"我今天考试"）可以记录；AI 只观察到"今天任务完成少"，不能直接断言"用户生病"或"心理状态异常"。应区分 Known State（可直接参与规划）与 Possible State（优先确认）。
- **敏感状态要委婉。** "昨天执行情况和平时差异比较明显，今天状态还好吗？"而不是"你是否生病了"。

## 用户主动输入与 AI 判断并存

用户可以主动说：今天很累 / 今天只有 2 小时 / 最近状态很好 / 最近工作很多 / 今天要出门。

如果用户没有主动说明，AI 可以根据 History、Evidence、执行时间、已知 Context、授权数据做判断；**但证据不足时应优先询问，而不是把猜测写成事实。**

# 5. Progress State

表示"用户相对于 Goal / GoalNode 当前真实推进到了哪里"。

它不是只根据"完成多少 Mission"计算，还可能结合 Evidence、Evaluation、Mastery、Execution History、历史 Recall、真实应用结果。

```text
Flutter
├── Widget       已基本掌握
├── Layout       已推进
├── Navigation   已基本掌握
├── State        当前阶段
└── Network      尚未开始
```

## 规则

- ProgressState 是 **Derived Data**：损坏、删除或模型升级后，应该能重新读取 Mission / ExecutionEvent / Evidence / Evaluation 重新生成。
- 它是"缓存后的智能结论"，不是唯一历史来源。
- **Mastery 由 ProgressState 表达，不能直接写到 GoalNode 上。**
- GoalNode 描述"大纲是什么"，ProgressState 描述"用户走到了哪里"。

# 6. Reflection 与 Derived Memory

## 6.1 Reflection

长期方向上有价值，但不是当前闭环的必需对象。未来可以作为 Mission Reflection、Daily Reflection、Goal Reflection 独立扩展。

当前 Raw History 已经保证了未来添加 Reflection 时不会丢失基础材料。

## 6.2 Derived Memory

从 Execution History、Failure、Evaluation、ContextState、Progress 中提炼：

```text
用户经常低估某类任务时长
晚上学习效果较差
某种帮助方式效果更好
```

属于 Derived Data，**必须可以重新生成**。可以修改、推翻、重新生成——因为 AI 判断可能错误。

# 7. Data Access 与 Context Export

## 7.1 Evidence Provider

不同工具可以成为不同 Evidence Provider：Git、GitHub、Camera、Gallery、Files、Health、Calendar、External App、MCP、Skill、AI Interview。

未来 AI 可以主动观察（在用户授权下）：

> 检测到相关 Git Commit，需要将它作为这个 Mission 的 Evidence 吗？

## 7.2 Data Access Philosophy

只要某类数据确实可以改善规划、监督、验证或理解能力，并且用户明确授权，就可以考虑接入。

但：**能获取 ≠ 应该获取。** 没有明显价值的数据，不需要为了"AI 知道更多"而强行收集。

## 7.3 Context Export

支持导出完整个人成长上下文——不只是任务列表：

```text
Goal Tree / Current Plan / Plan History / Mission History
Evidence / Evaluation / Knowledge State / Assistance History
Context State / Failure Patterns / Progress / Reflection / Derived Memory
```

这样更强大的外部模型可以直接进行高级分析：

> 根据我最近 90 天真实执行情况，重新设计下一阶段计划。

而不是每次从头解释自己是谁。

# 8. 规划尺度

## 8.1 年 / 月 / 日多层规划

```text
Year   主要表达方向
Month  主要表达阶段目标
Day    主要表达实际行动
```

```text
越远 → 越抽象
越近 → 越具体
```

不应该提前数月精确决定某一天具体学习哪个 API。

## 8.2 Planning Horizon 动态变化

不同 Goal 不应该拥有相同规划深度。应根据 Goal 难度、时间跨度、用户可投入时间、当前能力、历史执行速度、Goal 确定程度动态决定规划粒度。

```text
2 周 Goal  → 可以直接规划每日 Mission
1 年 Goal  → 年度方向 → 月阶段 → 逐渐展开到每日 Mission
```

## 8.3 Plan History

保留：

```text
Original Plan → Actual Execution → Revised Plan → Reason
```

未来可以让 AI 判断：哪类任务经常延期、哪种规划总是失败、哪种估时偏差最大、哪些阶段经常需要补课。

# 9. 长期指标

核心指标不应只是 `Completion Rate`，而应逐渐关注 `Human Capability Growth`：

```text
Knowledge Growth / Skill Growth / Independence
Execution Stability / Decision Quality / Goal Progress / Habit Stability
```

展示方式：Knowledge Growth、Skill Growth、Goal Progress、Independence、历史对比、重要里程碑。

**奖励机制暂不优先**——不做等级、金币、连续签到、排行榜、经验值、虚拟奖励。成长本身应该成为奖励。

---

# 10. 明确不打算做的事

```text
让 AI 替用户生活
用模拟数据填充 AI 缺失的位置
以"完成率"为唯一成功指标
用金币 / 等级 / 排行榜驱动用户
为了架构漂亮而提前建立复杂 Agent / MCP / Memory 系统
```

最终：

```text
AI 看得更广 / 想得更远 / 记得更多 / 帮助规划 / 发现问题 / 提供知识 / 校正方向

但是

用户理解 / 用户判断 / 用户行动 / 用户经历 / 用户成长
```
