# Mission Book — 产品纲领

> 这是 Mission Book 的产品宪法。未来具体实现可以改变，但如果某个设计明显违背本文档的核心目标，就应该重新思考该设计是否适合 Mission Book。
>
> 本文档区分两类内容：
>
> - **原则** — 已经确定。实现时必须遵守，违背需要先改这份文档。
> - **方向** — 长期要做，当前不实现。落地细节见 [未来方向](未来方向.md)。
>
> 本文档不写 UI、不写技术架构、不写数据库 Schema、不写 Agent 实现方案。

---

# 1. Mission Book 是什么

Mission Book 是一个以**人的长期成长**为核心的 AI 辅助规划、执行、验证与反思系统。

它不是传统 Todo App，也不是以"尽可能替用户完成事情"为目标的通用 AI Agent。

它希望建立的长期循环：

```text
Goal
 ↓
Plan
 ↓
Mission
 ↓
User Action
 ↓
Evidence
 ↓
AI Evaluation
 ↓
Memory
 ↓
Reflection
 ↓
Replanning
 ↓
Next Mission
```

系统最终追求的不是：

> AI 帮用户完成了多少事情。

而是：

> 用户本人是否因为长期使用 Mission Book 而真正变强。

**一句话定义**：一个利用 AI 的知识、分析、规划、监督和验证能力，帮助用户把长期目标转化为真实行动，并通过持续反馈让能力真正沉淀到用户自身的个人成长系统。

---

# 2. 核心理念：AI 的能力不是用户的能力

AI 可以搜索、总结、分析、推理、比较、规划、生成代码、调用工具、处理多模态信息。

但：

```text
AI 写出代码        ≠  用户会写代码
AI 给出正确判断    ≠  用户拥有判断能力
AI 制定计划        ≠  用户能够执行计划
AI 理解知识        ≠  用户已经理解知识
```

因此，不能把**提高 AI 输出能力**误认为**提高用户能力**。

## 原则：Human Capability First

Mission Book 在很多情况下应该问：

> 这件事情，究竟应该由 AI 完成，还是值得让用户自己掌握？

通常：

**可以更多交给 AI** — 搜索资料、查 API、信息整理、重复劳动、数据比较、基础计算、文档摘要、信息聚合、环境观察、非核心知识查询。

**更值得让用户掌握** — 理解、判断、推理、设计、调试思维、核心技能、决策、创造、实际操作、真实世界行动。

这个边界并不固定，它取决于 **用户的 Goal**：

- 如果用户希望成为 Flutter 开发者，Flutter 架构能力值得训练。
- 如果用户只是需要偶尔维护一个页面，很多具体 API 完全可以交给 AI。

因此重要判断标准是：

> 这是不是用户未来真正希望拥有的能力？

---

# 3. 核心理念：成长必须发生在人身上

```text
AI 看得更广 / 想得更远 / 记得更多
AI 帮助规划 / 发现问题 / 提供知识 / 校正方向

但是

用户理解 / 用户判断 / 用户行动 / 用户经历 / 用户成长
```

**AI 是能力放大器。成长必须发生在人身上。**

# 4. AI 的角色与边界

## 4.1 AI 的角色

Mission Book 中的 AI 更接近 Mentor、Planner、Analyst、Evaluator、Supervisor、Advisor、Reflector。

AI 的价值之一是帮助用户调用原本不属于自己知识边界的视角。例如一个 Flutter 学习问题，背后可能同时涉及软件工程、教育学、认知心理学、项目管理、时间管理、行为习惯与学习科学。

但真正需要成为用户能力的部分，仍然要经过：

```text
理解 → 行动 → 错误 → 验证 → 反思 → 再次行动
```

## 4.2 原则：AI 可以给答案

Mission Book 不采用"AI 永远不能直接告诉用户答案"这种极端原则。

人的时间、耐心、注意力、情绪、认知资源都是有限的。一个低价值问题让用户无意义地卡很久，并不会自动产生学习价值。

AI 应该控制的是：

> **什么时候给答案、给多少、用什么方式给。**

而不是简单决定给 / 不给。

## 4.3 原则：最终决定权属于用户

AI 可以拥有观察权、分析权、建议权、提醒权、质疑权、监督权、重新规划建议权。

但**最终决定权属于用户**：

```text
AI    观察 → 分析 → 建议
USER  决定 → 行动 → 承担结果
```

AI 可以明确表达"我不建议这样做"。但如果用户理解风险后仍然坚持，系统应该尊重最终决定。

**正式进入执行计划的 Mission 必须经过用户确认。** 原因是 AI 不可能完整了解现实世界中的全部情况——临时加班、家庭事务、电脑不在、身体状态、突发事件，这些只有用户知道。

```text
AI Proposal → Explain → User Confirm → Mission Active
```

## 4.4 原则：AI 可以质疑用户

Mission Book 不应该把用户的所有决定都视为正确。AI 可以质疑 Goal、Mission、时间安排、学习策略、任务难度，以及用户对自己掌握程度的判断。

但质疑必须有依据。第一次对某个重要 Goal 提出质疑时，应解释：

```text
为什么困难 → 依据是什么 → 风险是什么 → 有哪些替代方式
```

例如：

```text
保持目标 → 延长周期
保持周期 → 提高投入
缩小阶段目标 → 保持当前负荷
```

而不是简单说"这个目标不现实"。

## 4.5 原则：默认 AI 性格是陪伴型监督者

当前默认不应该是冷酷教官、机械规则执行器，或无条件鼓励者，而更接近**陪伴型监督者**：

```text
有判断 + 有依据 + 有温度
```

AI 可以指出问题，但不应该随意否定用户、因一次失败责备用户、使用羞辱式语言、为严格而严格、或为安慰而无原则降低要求。

## 4.6 原则：理解失败 ≠ 无限纵容失败

第一次没有执行 → 理解原因 + 适度调整。

连续第二次没有执行 → 进一步分析 + 重新考虑任务设计。

持续第三次 → 停止机械调整，进入问题诊断，开始讨论：

- Goal 还重要吗？
- 任务是否不合理？
- 是否一直在逃避困难？
- 是否时间安排错误？
- 是否能力前置不足？
- 是否现实环境已经变化？

核心思想是：

> 不要继续用相同方法重复失败。

# 5. Mission 的性质

## 5.1 原则：Mission 不等于普通 Task

普通 Todo 往往只有 `Task → Done`。

Mission 应拥有更完整的语义：

```text
Mission
├── 对应哪个 Goal
├── 为什么现在做
├── 要做什么
├── 如何做
├── 验收方向
├── 预计投入
├── 实际执行
├── Evidence
├── Evaluation
├── Reflection
└── 对后续 Plan 的影响
```

因此 Mission 的最终评价不应该永远只有 `Done / Not Done`。

## 5.2 原则：Mission 必须具有方向感

重要 Mission 应尽量回答四个问题：

```text
Why     为什么现在做
What    这次具体做什么
How     建议怎么做
Verify  需要达到什么程度才算有效
```

这样用户在开始之前就知道：我为什么做这件事情，以及应该做到什么程度。

## 5.3 原则：Execution 与 Verification 不是一回事

```text
执行完成 ≠ 验证通过 ≠ 已经学会 ≠ 长期掌握
```

用户可以完成了本次行动，但学习目标只部分达到。这两件事不矛盾，必须分开表达。

## 5.4 原则：部分达成不让旧 Mission 永久挂起

如果 Mission 已经认真执行，只是局部目标没有达到，原 Mission 仍然可以结束。

不应该长期出现"半完成 / 半完成 / 半完成"挂在任务列表上。更合理的是：原 Mission 结束 → 发现缺口 → 提出针对性的新 Mission → 用户确认。

## 5.5 原则：未完成 Mission 必须先诊断

Mission 未完成后，不应该直接延期。应该先问"为什么没有完成"。

可能原因：时间不足、任务太大、任务太难、没有兴趣、环境不允许、临时事情、状态不好、前置能力不足、单纯没有执行。

然后决定：`Delay / Split / Reduce / Replace / Add Prerequisite / Replan / Drop / Keep`。

```text
Failure → Diagnosis → Decision
```

# 6. 原则：失败是一级数据

失败不是垃圾数据。Mission Book 应记录：

```text
发生了什么 / 为什么失败 / 实际做了多少 / 在哪里停止
是否尝试过 / 是否超时 / 任务是否太难
状态是否变化 / 计划是否错误
```

例如：

```text
Planned: 120 min
Actual:  35 min
Result:  Not Completed
Reason:  Debug 时间严重超预期
Planning Effect: 下一次拆成更小 Mission
```

失败可以帮助系统更了解用户、任务难度、真实时间成本、错误估计、执行习惯和当前能力边界。

因此 `Failed Mission` 依然可能产生 `Useful Progress Data`。

**系统应该鼓励：真实失败 > 虚假成功。** 因为真实失败可以改善规划，虚假成功只会污染 Memory。

# 7. Evidence

## 7.1 原则：Evidence 是核心基础设施

Evidence 不是普通附件。它代表：

> 能够帮助 AI 理解用户真实行动结果的信息。

Evidence 可以来自 Camera、Screenshot、Image、Video、Text、File、Code、Git Commit、Repository、Health Data、App Export、AI Interview、Manual Record、External Tool。

不要求用户把现实世界中的所有结果都转换成文字。AI 可以综合多个 Evidence 进行判断。

## 7.2 原则：Evidence 不是绝对真相

用户可以撒谎，也可能提交错误证据。Mission Book 无法真正控制用户。

Evidence 的作用不是消灭欺骗，而是：

> 增加错误陈述的成本，提高系统获取真实反馈的概率。

## 7.3 原则：Evidence 与 Evaluation 必须分离

```text
Evidence   = 事实 / 原始材料
Evaluation = AI 对这些材料的判断
```

例如 `Git Commit` 是 Evidence；"这次代码说明用户已经基本理解 Navigator" 是 Evaluation。

分开的理由：AI 的判断会变化，模型会更替。今天 Model A 给出 Understanding 72，一年后 Model B 可以重新读取原始 Evidence 与 ExecutionHistory，重新生成 Evaluation。

因此：**原始 Evidence 与 Raw History 应比某一次 AI 判断更加基础和稳定。**

## 7.4 原则：Manual Override 可以存在，但必须留痕

用户应该能够强制完成某个 Mission。但系统要能区分：

```text
Completed + Verification: Verified
Completed + Verification: Unverified + Manual Override: true
```

Mission Book 不应该阻止用户控制自己的任务，但也不应该把无法验证的信息默认为高可信事实。

# 8. Goal Tree 与规划

## 8.1 原则：大纲可以修改，但不能没有大纲

Mission Book 必须拥有长期大纲：

```text
Software Development
├── Flutter
│   ├── Dart
│   ├── Widget
│   ├── Navigation
│   ├── State Management
│   └── Project Practice
├── Software Design
├── CS Foundation
└── Project Experience
```

Goal Tree 防止长期运行过程中方向漂移：忘记方向、过度关注短期任务、上下文漂移、模型切换后丢失整体结构。

AI 可以建议新增、删除、合并、拆分、调整顺序、修改优先级，但重要变化应该**记录原因 + 用户确认**。

用户应该始终可以回答：

> 我今天做的事情，在长期 Goal Tree 中到底处于什么位置？

## 8.2 原则：紧急不等于重要

不应机械采用 `Urgent > Important`。AI 应同时判断：紧急程度、实际后果、长期价值、时间成本、Goal 重要程度。

对于"低价值但必须完成"的事情，AI 可以建议：

> 使用最低必要投入完成，不要让它吞掉核心长期 Goal。

Mission Book 应主动保护长期成长不被大量低价值紧急事务侵蚀。

## 8.3 原则：可持续负荷

Mission Book 不追求最大化时间利用率。

如果用户有 6 小时可支配时间，默认可以只规划约 40%～60%（2.5h～3.5h Mission）。剩余时间属于娱乐、休息、社交、发呆、临时事件、Buffer 和自由生活。

**不应该默认把生活全部变成"任务"。**

40%～60% 是默认参考，不是绝对限制。如果某阶段值得临时增加投入，AI 可以询问：

> 今天如果额外增加 1 小时，可以完成当前阶段。你愿意让出这段时间吗？

额外时间应该通过**协商**获得，而不是自动占用。

## 8.4 原则：长期持续性高于短期极限效率

不追求：

```text
每天计划 6 小时 → 坚持 5 天 → 崩溃
```

更希望：

```text
每天稳定推进 → 持续数月
```

Mission Book 应保护：

> 用户愿意第二天重新开始的能力。

## 8.5 原则：Mission Debt 不应无限累积

未完成 Mission 不应该不断 `Tomorrow / Tomorrow / Tomorrow`，否则新 Mission + 旧 Mission + 更旧 Mission 会让计划彻底崩坏。

AI 应判断旧 Mission 是否仍有价值：保留、延期、合并、替代、删除。

如果知识已经自然掌握、新 Mission 已经覆盖旧目标、Goal 已变化或任务价值下降，AI 可以主动建议：

> 删除这个 Mission。

Mission Book 不追求完成历史计划里的每一项，真正追求的是：

> Goal 所需要的能力与结果是否已经获得。

## 8.6 原则：动态难度

应动态调整 Mission 难度、任务规模、AI Assistance、验收标准与学习速度。

连续表现很好 → 提高挑战、减少提示、提高独立要求、加快进度。

持续表现困难 → 降低粒度、增加辅助、增加前置学习、放缓进度。

目标是寻找**合理挑战区**：既不是一直很简单，也不是持续失败。

## 8.7 原则：当用户说"不想干"时需要动态判断

系统不应该永远"好，那今天全部取消"，也不应该永远"必须坚持"。而应该看：最近是否持续高负荷、是否已经休息多天、是否连续逃避、当前 Context、Goal 当前阶段。

- 如果已经连续高强度执行 → 完全休息可能合理。
- 如果已经连续多天没有推进 → 保留一个很小的核心 Mission 可能更合理。

AI 给出建议后，由用户决定。

## 8.8 原则：休息是计划的一部分

休息不是计划之外的东西。AI 可以建议"今天减少任务"甚至"今天停止继续学习"。用户接受后，可以生成具体休息安排。

# 9. 规划原则（方向）

以下方向已经确定，但当前不实现，细节见 [未来方向](未来方向.md)。

## 9.1 年 / 月 / 日多层规划

```text
Year   主要表达方向
Month  主要表达阶段目标
Day    主要表达实际行动
```

原则：

```text
越远 → 越抽象
越近 → 越具体
```

不应该提前数月精确决定某一天具体学习哪个 API。

## 9.2 Planning Horizon 动态变化

不同 Goal 不应该拥有相同规划深度。应根据 Goal 难度、时间跨度、用户可投入时间、当前能力、历史执行速度、Goal 确定程度动态决定规划粒度。

## 9.3 Plan History

计划调整后不应简单覆盖旧计划，应保留：

```text
Original Plan → Actual Execution → Revised Plan → Reason
```

这些数据未来可以让 AI 判断：哪类任务经常延期、哪种规划总是失败、哪种估时偏差最大、哪些阶段经常需要补课。

## 9.4 临时事件允许改变计划

现实不会按照计划运行。突然出现工作时，可以重新评估 `Current Plan + New Event + Remaining Time → Replan Proposal`。原 Mission 可以延后、拆分、缩短、删除、改时间，但正式修改仍应经过用户确认。

## 9.5 Context State

Mission Book 不只需要知道"用户长期是什么样"，还需要知道"用户现在是什么状态"：身体不适、情绪变化、工作繁忙、临时项目、旅行、考试、睡眠不足、可用时间减少、当前状态很好。

这些信息具有**时间性**，不应该永久存在，需要复查时间。

一个临时状态应该包含：`State / Start / Expected End / Source / Confidence / Planning Impact / Follow-up Time`。

默认有效期不是事实：

```text
7 天后：
现在感觉怎么样？
[恢复] [还有一些] [仍需休息]
```

Mission Book 的主动性不仅来自提醒用户做任务，还来自：

> 记得以前发生过什么，并在合适时间回来询问。

## 9.6 敏感状态需要谨慎判断

```text
昨天没完成 Mission
```

不能直接推断"用户生病"。更合理的是：

> 昨天执行情况和平时差异比较明显，今天状态还好吗？

应区分 `Known State`（可直接参与规划）和 `Possible State`（优先确认）。

## 9.7 Raw History 与 Derived Memory

```text
Raw History    真实发生过的事情，尽量保持原始
Derived Memory AI 根据历史得出的判断，可以修改、推翻、重新生成
```

例如 `用户经常低估编程任务时间` 属于 Derived Memory，因为 AI 判断可能错误。

## 9.8 Data Access Philosophy

只要某类数据确实可以改善规划、监督、验证或理解能力，并且用户明确授权，就可以考虑接入。

但：**能获取 ≠ 应该获取。** 仍需判断是否与 Goal 有关、是否能改善 Planning / Evidence / Evaluation、是否有实际价值。

没有明显价值的数据，不需要为了"AI 知道更多"而强行收集。

## 9.9 Context Export

应支持导出完整个人成长上下文，而不只是任务列表：Goal Tree、Current Plan、Plan History、Mission History、Evidence、Evaluation、Knowledge State、Assistance History、Context State、Failure Patterns、Progress、Reflection、Derived Memory。

这样更强大的外部模型可以直接进行高级分析，例如：

> 根据我最近 90 天真实执行情况，重新设计下一阶段计划。

而不是每次从头解释自己是谁。

## 9.10 通知

通知不是简单 Alarm。未来可以结合上下文：

> 今天的核心 Mission 还没有开始。

> 最近数据显示，你上午学习 Flutter 的完成率更高。

> 今天剩余时间不够，我建议取消次要 Mission。

> 前几天你说身体状态不好，现在恢复得怎么样？

通知是 Mission Book 主动参与用户现实生活的重要入口。

# 10. 长期指标

**原则：核心指标不是任务完成率。**

最重要的长期指标不应该只是 `Completion Rate`，而应该逐渐关注 `Human Capability Growth`：Knowledge Growth、Skill Growth、Independence、Execution Stability、Decision Quality、Goal Progress、Habit Stability。

**原则：奖励机制暂不优先。**

当前不需要等级、金币、连续签到、排行榜、经验值或虚拟奖励。因为成长本身应该成为奖励。更重要的是让用户看到：

```text
30 天前不会 → 今天已经会了
```

可以展示 Knowledge Growth、Skill Growth、Goal Progress、Independence、历史对比和重要里程碑——这些本身就是反馈。

# 11. 数据与模型

## 11.1 原则：模型可以更换，数据不能丢

用户长期数据应该成为 **Mission Book 自己的资产**。AI 是可替换的分析层。

未来可能使用 OpenAI、Claude、Gemini、Local Model 或其他模型，但 Goal、Plan、Mission、ExecutionPlan、ExecutionHistory、Evidence、Evaluation 这些概念应该依然存在。

> AI 是领域系统上的智能层，而不是领域本身。

## 11.2 原则：Raw History 必须保留

不应该只保存最终结果。

```text
原计划怎么安排 / Mission 为什么产生 / ExecutionPlan 是什么
实际几点开始 / 暂停了几次 / 延长了多久
最终产生了什么 Evidence / AI 当时如何 Evaluation / 后来为什么 Replanning
```

这些数据未来都可能成为更强 AI 的分析材料。`Mission = Completed` 远远不足以描述真实发生的事情。

## 11.3 原则：AI 判断不能污染原始历史

```text
Raw Fact → Derived Evaluation
```

而不是：

```text
AI Evaluation → 修改 Raw Fact
```

## 11.4 原则：AI 调用不与原始事实强绑定

用户提交 Evidence 时：

```text
正确：Evidence 保存成功 → 等待 Evaluation → AI Evaluation
错误：保存 Evidence + AI 请求 + Evaluation + Replanning 必须同时成功
```

AI 可以失败、超时、断网、重试、换模型，但用户已经提交的 Evidence 不能因此消失。

# 12. 多端与形态

**原则：多端不是为了所有平台都做一样的 App。**

Mission 会发生在不同现实场景：

```text
手机更适合：通知 / 拍照 / 截图 / 快速记录 / 运动数据 / 随手 Evidence
电脑更适合：编程 / Git / 文件 / 长文本 / 深度分析 / 复杂 Evidence
```

当前阶段不需要刻意把手机端和桌面端做成完全不同产品。优先完成核心闭环，后续差异应该由真实使用场景自然产生。

---

# 13. 当前开发原则

**原则：先做闭环，不做架构。**

不要因为这些技术很吸引人，就过早建立多 Agent、复杂 MCP、大型 Memory System、复杂 Skill Runtime、企业级基础设施。

```text
产品闭环 > 用户体验 > 核心数据 > 基础 AI 能力 > 复杂 Agent 架构
```

第一阶段首先证明这一条链真正好用：

```text
Goal → Plan → Today → Mission → Execute
→ Evidence → Evaluation → Review → Tomorrow
```

## 13.1 判断一个功能是否应该加入

1. 它解决 Mission Loop 中什么问题？
2. 它帮助用户成长，还是只是增加自动化？
3. 它现在真的有必要吗？
4. 没有它，核心闭环是否仍然能运行？
5. 它产生的数据未来有价值吗？
6. 它是否帮助 AI 更理解用户真实状态？
7. 它是否让用户更接近 Goal？
8. 它是否让系统复杂度明显增加？
9. 这种复杂度目前是否值得？

## 13.2 当前最重要的事情

不是建立万能 AI Agent，也不是一开始就建立个人操作系统，而是：

> **做出一个最小、完整、真实可长期使用的成长闭环。**

然后：

```text
使用 → 产生真实数据 → 发现问题 → 调整设计 → 加入真正有价值的能力
```

Mission Book 应该随着用户一起成长。

## 13.3 Flutter 项目原则

Mission Book 同时也是开发者学习 Flutter 的真实项目。开发过程本身应该服务两个 Goal：

```text
Build Mission Book + Learn Flutter
```

不应该为了快速开发，让 AI 大量生成开发者完全无法理解的 Flutter 架构。AI 可以解释、指导、Debug、评审、给必要示例、拆分任务、提醒设计问题，但正在学习的核心能力应优先保证真正理解。

---

# 14. 最终原则

Mission Book 不试图让 AI 替用户生活。

```text
AI 看得更广 / 想得更远 / 记得更多 / 帮助规划 / 发现问题 / 提供知识 / 校正方向

但是

用户理解 / 用户判断 / 用户行动 / 用户经历 / 用户成长
```

**AI 是能力放大器。成长必须发生在人身上。**
