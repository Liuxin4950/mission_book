# Mission Book — 界面与交互

> 本文档定义信息架构、页面结构、核心交互链与视觉基调。
>
> 视觉与页面布局的**事实标准是 `docs/ui设计手册/` 里的设计稿**。本文档把设计稿转写成文字规则，并在设计稿未覆盖的地方给出定义（会明确标注）。
>
> 本文档描述目标行为与交互口径，不描述 Flutter 实现。

---

# 1. 品牌与视觉基调

## 1.1 品牌

```text
名称      Mission Book
主标语    让每一个行动，通向更好的自己。
英文       Turn direction into action.
           A better you, one mission at a time.
副标语     Small steps. A bigger you.
```

三个支柱：

```text
Plan   看清方向
Act    专注执行
Grow   持续成长
```

品牌链路：

```text
Goal → Mission → Action → Evidence → Growth
```

## 1.2 视觉基调

```text
安静 / 克制 / 有呼吸感 / 像一本可以长期书写的册子
```

不是效率工具，不是游戏化打卡。**不使用金币、等级、连续签到、排行榜、经验值。**

## 1.3 取色（已从设计稿取样，实现时以设计稿为准）

| 用途 | 近似值 | 说明 |
| --- | --- | --- |
| 页面背景 | `#F7F5ED` | 暖白 |
| 卡片 / 次级面 | `#F6F3EB` | 与背景差异极小，靠发丝描边分层 |
| 主色（实心按钮、强调） | `#4A6A57` | 深墨绿 |
| 进度 / 强调绿 | `#4F8768` | 比主色亮，用于进度条与已完成标记 |
| 主文本 | 近黑 | 深灰黑，不用纯黑 |
| 次级文本 | 中灰 | 用于说明、路径、时间 |
| 分隔线 | 极浅灰 | 发丝线，1px |

金色 / 米色只用于插画和点缀（如封面上的菱形标记），不用于功能语义。

## 1.4 字体与排版

- 大标题使用衬线体（中英一致），营造"书册"感；正文使用无衬线体。
- 中英混排：英文用于品牌、区块标题（`Why` / `What` / `How` / `Verify`、`CURRENT MISSION`）与导航标签；**所有功能文案、按钮、提示、错误信息用中文**。
- 大量留白；信息块之间用间距和发丝线分隔，不靠重色块。
- 卡片圆角较大，按钮为胶囊形或通栏圆角矩形。

## 1.5 语气

界面文案的语气与 AI 性格一致：**陪伴型监督者**——有判断、有依据、有温度。

- 陈述事实，不评判用户（"已执行，但未完成验证闭环"，而不是"你失败了"）
- 建议用"建议 / 可以"，命令用"请"
- 不谄媚、不加油打气式的空话

# 2. 信息架构

底部四个 Tab：

```text
Today    今天要做什么
Goals    长期方向与大纲
History  历史记录
Me       设置与个人数据
```

```text
Today
├── 当前 Mission 卡
├── 今日列表
└── See All → 全部 Mission

Goals
├── Goal 列表（Active / Paused / Achieved）
└── Goal Detail
    └── 目标路径树（GoalNode Tree）

History
└── 按时间倒序的执行记录

Me
└── 设置 / 导出 / 关于
```

Mission 的页面链路：

```text
Today / Goals
   ↓
Mission Detail
   ↓
In Mission（执行中）
   ↓
End Mission（结束确认）
   ↓
Add Evidence（按 VerificationPolicy 进入）
   ↓
Result（等待评价 / 查看结果）
```

Failure Diagnosis 使用 Bottom Sheet，不增加独立顶层页面。

**待定**：设计稿未覆盖 History 与 Me 两个页面。当前定义最小范围——History 展示按时间倒序的 Mission 执行记录（标题、日期、实际 Focus、结果），Me 展示设置、数据导出与关于。具体设计待补设计稿。

# 3. 启动页

```text
Mission Book 标志
山间小路的线条插画（一个标记点从起点走向终点）
"正在为你准备今天的旅程…"
进度条
```

启动页只在应用启动时短暂出现。**不要用它来加载业务数据阻塞用户**——数据加载失败时进入可重试的错误态，而不是永远停在启动页。

# 4. Today

## 4.1 结构

```text
Good afternoon.
今天继续推进 State。            [头像]

┌─────────────────────────────────────┐
│ CURRENT MISSION            [Preferred]│
│ 理解 setState 与 rebuild              │
│ Flutter > State > Fundamentals        │
│                                       │
│ 为什么现在做                           │
│ 为 Mission Book 的交互页面建立状态管理基础│
│                                       │
│ ⏱ 45 min        [  Start Mission  →  ]│
└─────────────────────────────────────┘

Today · 3 Missions                 See All >

○  Route recall      复习 Navigator 与路由栈     15 min
●  State fundamentals 理解 setState 与 rebuild    45 min
○  Mission Book UI    实现首页基础布局            50 min

[Today] [Goals] [History] [Me]
```

## 4.2 规则

- 问候语按时段变化（Good morning / afternoon / evening），副标题一行，可以引用当前推进的 GoalNode 或今天的重点。
- **当前 Mission 卡**只展示一个 Mission：取"需要立刻处理"的优先级——Executing > Paused > Ready。没有则展示今天第一个 Ready。
- 卡片必须展示：Title、Goal / GoalNode 路径、时间策略标签、Why 摘要、计划时长、主操作按钮。
- 主操作按钮文案随阶段变化（见 §6）。
- 今日列表按时间排序，已完成项显示为填充圆点，未完成项为空心圆。
- "See All" 进入全部 Mission 列表。
- 已完成项保留在 Today 直到当天结束，不清空——用户需要看到今天真正做了什么。

## 4.3 完成记录

首页下方展示执行活动：

- 最近 7 天：`完成数 / 计划数`
- 近 30 天：完成格子（颜色深度表达单日完成数）
- 完成数来自真实 END 事件，**不由计划日期推断**
- 无数据时显示明确空状态，不显示空白块

# 5. Mission Detail

用户开始之前可以看到完整的 Why / What / How / Verify：

```text
←   Mission Detail                    ⋯

理解 setState 与 rebuild        [Preferred]
Flutter > State > Fundamentals

Why
为 Mission Book 的交互页面建立状态管理基础，
是进入真正交互开发的第一步。

What
理解 setState 的工作原理，掌握触发 Widget rebuild
的条件和常见场景。

How
1. 阅读官方文档与示例
2. 编写简单示例并运行实验
3. 记录不同场景下的 rebuild 结果
4. 总结自己的理解

Verify
提交代码示例与总结笔记，说明对 setState 触发时机的理解。

⏱ 45 min        📅 Sep 13, 2026

[         Start Mission  →         ]
```

## 规则

- 四块内容来自 `Mission.why` + `ExecutionPlan.objective / steps / verificationCriteria`，组合展示，不重复存储。
- 缺失的块不显示空标题。
- 主操作随 LifecycleStage 变化：

| Stage | 主操作 |
| --- | --- |
| SCHEDULED / READY | 开始 Mission |
| EXECUTING | 继续执行 |
| EVIDENCE_PENDING | 整理 Evidence |
| EVALUATION_PENDING | 查看结果 |
| CLOSED | 查看结果 |

- `⋯` 提供编辑、改时间、取消 Mission。**START 后 ExecutionPlan 不可编辑。**

# 6. In Mission

```text
←   In Mission                        ⋯

理解 setState 与 rebuild
Flutter > State > Fundamentals

        ╭───────────────╮
        │    31:42      │      圆环进度
        │ Focus 31 min  │
        │ Planned 45 min│
        ╰───────────────╯

┌──────────────────────────────────────┐
│  🌿  Small steps make a bigger you.  │
└──────────────────────────────────────┘

[  ⏸ Pause  ]  [  ⏹ End  ]

        +  Extend Time

┌──────────────────────────────────────┐
│ ◎ Current Objective                  >│
│   理解并实践 setState 触发 rebuild 的机制│
└──────────────────────────────────────┘
```

## 规则

- 进入页面前必须已经完成 StartMission。
- 圆环展示 Focus 占计划时长的比例；时间文本展示 **Focus Time**，同时展示 Planned。
- Pause 期间圆环停止推进、Elapsed 继续增加。
- Extend Time 产生 EXTEND 事件，**不修改原计划时长**。
- Current Objective 可展开查看完整 ExecutionPlan。
- 计时不依赖常驻定时器或后台服务；页面上的计时器只用于刷新显示，真实时间始终由执行事件计算。

## 到达计划时间

当 Focus 达到计划时长时，**不自动结束**，弹出询问：

```text
本次 Mission 的计划时间已经到了。
[ 结束 ]   [ 继续 ]
```

# 7. End Mission

```text
←   End Mission

              ✓

    这次 Mission 已完成了么？
根据实际情况选择结果，这将影响后续的验证流程。

┌──────────────────────────────────────┐
│ ✓  已完成                             │
│    我已经完成了计划的内容。             │
├──────────────────────────────────────┤
│ ○  未完成                             │
│    我未能完成计划的内容。               │
└──────────────────────────────────────┘

📄 接下来
根据该 Mission 的验证策略，下一步你需要：
提交 Evidence 进行验证。

[              继续  →              ]
```

## 规则

- "接下来"的说明必须**如实反映该 Mission 的 VerificationPolicy**：

```text
SELF_REPORT         → 本次 Mission 将直接结束
OPTIONAL_EVIDENCE   → 可以选择提交 Evidence，也可以直接结束
REQUIRED_EVIDENCE   → 需要在今天 24:00 前提交 Evidence
```

- 选择"未完成"后，展示 Failure Reason 选择（可为空，不强制填写说明）。
- 从系统通知点击"停止"时：先写 PAUSE，再打开这个页面；用户取消则保持 Paused。

# 8. Add Evidence

```text
←   Add Evidence

[ Draft ] [ Files ] [ Camera ] [ Note ]

┌ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ┐
        🖼  添加证据
   支持图片、文件、代码、笔记等多种形式
└ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ┘

已添加 (2)
▣  setstate_demo.png            ×
   PNG · 2.4 MB
▣  notes.md                     ×
   Markdown · 1.1 KB

[ 添加说明（可选）              ]

[       Finalize Submission  →      ]
提交后将作为正式 Evidence 保存。
```

## 规则

- Finalize 前是 **Draft**，可以自由新增、编辑、删除、替换。Draft 不属于正式历史。
- 页面必须让用户清楚这一点：草稿区与正式区文案不同，按钮明说"Finalize Submission"，下方提示"提交后将作为正式 Evidence 保存"。
- 附件选择后立即复制进应用私有目录；数据库只保存相对 storageKey，**不保存来源文件的绝对路径**。
- 单附件上限 20 MB；删除 Draft 附件时同步删除私有目录副本。
- 图片在 Draft 与 Result 页面直接预览。
- **Finalize 是 Draft → Formal Evidence 的唯一入口。**
- 本版 Evidence 类型：文字、代码、图片、文件、手动记录。设计稿中的 Camera 对应图片类型；**本版不提供视频、Git Commit、健康数据等类型**。

## 本版的显示规则

真实 AI 尚未接入。本版**保留这个页面的结构与位置**，但：

```text
不生成任何分数
不生成任何评语
不生成任何建议
```

页面显示**执行事实**：

```text
Mission 标题与路径
执行结果（来自 UserReportedResult）
实际 Focus / Planned / 暂停次数
提交的 Formal Evidence 列表
```

并在评价区域明确显示：

> 智能评价暂未接入。

用户可以在此页确认并结束这次记录（Mission 关闭，`closureReason = EVALUATION_NOT_AVAILABLE`）。

**绝不允许**为了让页面好看而填入占位数字或模拟评语。

## 未来接入 AI 后

信息优先级：

```text
1. 做到了什么
2. 发现了什么
3. 仍有什么缺口
4. 下一步建议
5. Scores（默认折叠）
```

Scores 默认折叠，避免数字抢走评价的重点。

Partial Verification 可以提出 Recall / Supplement 建议，但**只有用户点击接受后才创建新 Mission**。

# 10. Goals

```text
←   Goals                             ⋯

[ Active ] [ Paused ] [ Achieved ]

┌──────────────────────────────────────┐
│ 🌿  学会 Flutter                    > │
│     系统学习 Flutter 开发，掌握核心概念  │
│     并能够独立开发应用。                │
│     ▓▓▓▓▓▓▓░░░░░░░░░                  │
│     6 / 12 nodes              50%     │
├──────────────────────────────────────┤
│ 🚩  完成 Mission Book               > │
│     ...                               │
└──────────────────────────────────────┘

[          +  新建目标           ]
```

## 规则

- 三个 Tab 对应 `Goal.status`：Active / Paused / Achieved（`DROPPED` 的 Goal 不出现在默认列表）。
- 每个 Goal 卡片展示：图标、标题、描述、进度条、`已完成节点数 / 活动节点总数`、百分比。
- 进度口径见 [领域模型 §10](领域模型.md)——这是"关联 Mission 的完成覆盖"，**不是掌握度**，UI 不得使用"已掌握""熟练"等措辞。
- 页面级主操作是底部通栏"新建目标"按钮，点击后选择"手动新建"或"从 JSON 导入"。

# 11. Goal Detail

```text
←   学会 Flutter                       ⋯

🌿  学会 Flutter
    系统学习 Flutter 开发，掌握核心概念
    并能够独立开发应用。

┌──────────────────────────────────────┐
│   6 / 12 nodes                50%     │
│   ▓▓▓▓▓▓▓▓░░░░░░░░░░                  │
└──────────────────────────────────────┘

目标路径

✓  Dart                              >
✓  Widget                            >
✓  Layout                            >
●  Navigation                    3 / 4 ∨
   ✓  Navigator                       >
   ●  Route                [ 正在学习 ]
   ○  Route Stack                     >
   ○  Deep Link                       >
○  State                         0 / 4  >
○  Network                       0 / 3  >
```

## 规则

- 节点状态只有三种，全部由关联 Mission 推出：

```text
✓  已完成        该节点存在已完成的 Mission
●  正在学习      该节点存在尚未关闭的 Mission
○  还没有记录    其余情况
```

- 右侧计数是该节点子树内的 `已完成 / 总数`。
- 展开 / 收起子节点。
- 点击节点进入该节点的任务视图（只显示与该节点关联的 Mission）。
- 页面级主操作是"创建任务"；**"新增根节点"放在"目标路径"区块内**，子节点新增放在对应节点的菜单内。
- 节点行的任务入口文案必须写明"建任务"，不得只写"任务"（容易被误读为分类名）。

# 12. 入口与按钮规则

**页面级主操作统一使用底部通栏按钮**（胶囊形、实心主色、带右箭头或加号图标），与设计稿一致。

```text
Today          → 卡片内的 Start Mission
Goals          → 底部「+ 新建目标」
Goal Detail    → 底部「创建任务」
Add Evidence   → 底部「Finalize Submission」
Result         → 底部「Back to Today」
```

- 按钮必须带中文文字，不使用纯图标表达主操作。
- 不使用右下角悬浮按钮——这与早期草案不同，以设计稿为准。
- 危险操作（删除 Goal、删除节点、取消 Mission）需要二次确认。

---

# 13. 表单规则

- 输入框必须有可见描边或填充，Focus 与 Error 状态有明确差异。
- 多行可选字段默认单行高度，随输入增长到最多三行，不预留大片空白。
- **窄屏打开短表单时不要自动唤起输入法**，用户点击字段后再输入。
- 表单内容区可滚动；键盘弹出时，标题与底部"取消 / 保存"仍在可达区域。
- 必填字段为空时显示就地错误，**不允许无反馈地忽略按钮点击**。
- 日期选择、时长选择使用系统或统一的自定义控件，不允许多种风格混用。

---

# 14. 反馈与状态

- 没有内容时显示明确空状态（一句说明 + 一个可执行的下一步），不显示空白页面。
- 加载中的主按钮保持与普通状态相同的高度，避免布局跳动。
- 错误提示必须说明"发生了什么"和"可以怎么做"，不使用"出错了"这类无信息文案。
- 破坏性操作确认框必须写清楚后果与不可逆性。

---

# 15. 交互原则

```text
主按钮高度在加载和普通状态下保持一致
内容最大宽度固定，桌面端不无限拉伸
小屏幕操作按钮自动纵向排列
没有内容时显示明确 Empty State
正式 Evidence 与 Draft 使用不同文案
AI 建议必须由用户确认后生效
不使用金币、等级、签到或排行榜
```
