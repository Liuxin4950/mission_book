# Mission Book 开发执行计划

> 这份计划既是开发路线，也是学习路线。目标不是尽快堆出全部代码，而是让每一步都能运行、能解释、能验证，并最终让项目作者能够独立维护 Mission Book。

## 1. 最终交付目标

完成一个 Windows 与 Android 均可真实使用的 Local First 应用，走通以下闭环：

```text
创建 Goal / 导入 GoalNode 大纲
→ 创建 Mission
→ Today 查看与开始
→ Pause / Resume / Extend / End
→ Self Report 或提交 Evidence
→ Result
→ 关闭并重启应用，状态和历史仍然正确
```

完成标准以 [本地应用规格](v1.0/本地应用规格.md) 为准，不以“页面看起来完成了”作为判断依据。

## 2. 教学式协作规则

每次只领取一个小任务，通常控制在一次学习能理解和验证的范围内。

每个任务按以下顺序进行：

1. **任务背景**：先说明这段代码解决什么问题，以及它位于整个应用的哪一层。
2. **必要知识**：只学习本任务马上会用到的 Flutter / Dart 知识，不提前灌输大量概念。
3. **你先实现**：核心代码优先由你亲手写；我先给目标、接口、提示和验收条件。
4. **共同检查**：你贴出代码或报错，我检查正确性，并解释问题产生的原因。
5. **自动验证**：运行格式化、静态检查和相关测试。
6. **手工验收**：在界面中实际执行本任务的用户路径。
7. **学习复盘**：你能回答“数据从哪里来、操作经过哪里、为什么这样设计”。
8. **小步提交**：一个通过验收的任务对应一个含义明确的 Git commit。

默认帮助强度：

- 第一次接触的概念：我给结构、示例和关键解释。
- 已经练过的概念：我只给目标和提示，让你独立完成。
- 连续卡住时：逐级增加提示，最后才给完整参考实现。
- 你写完后：我不仅检查“能不能跑”，也检查你是否真正理解。

## 3. 实现边界

### 本轮必须完成

- Goal 与 GoalNode Tree
- Goal Outline JSON 导入
- Mission 创建、计划与时间安排
- 真实执行事件与状态恢复
- Evidence Draft 与 Formal Evidence
- FailureRecord
- Today、Goals、History、Me 的最小可用页面
- 近 7 天 / 30 天执行记录
- Windows 与 Android 本地通知
- Windows 与 Android 实机验收

### 本轮不做

- AI Planner / Evaluation
- 云端、账号、同步
- PREFERRED 时间策略
- ContextState / ProgressState
- Goal Outline 自动合并
- 复杂路由框架、复杂依赖注入框架
- 为未来功能提前建立空表、空接口或占位字段

## 4. 建议架构

架构只分为四层，保持依赖方向清楚：

```text
Presentation  页面、组件、表单状态、页面 Controller
      ↓
Application   CreateMission、StartMission 等业务工作流
      ↓
Domain        实体、枚举、状态规则、时间计算
      ↓
Data          Drift、Repository、文件与通知实现
```

约束：

- Domain 不导入 Flutter，也不直接读数据库。
- 页面不直接拼写 SQL，也不同时修改多张表。
- 跨多张表的用户操作由 Application Workflow 发起，并在一个事务中完成。
- `ExecutionEvent[]` 是执行时间的事实来源，界面计时器只负责刷新显示。
- 先使用 Flutter 自带的 `ChangeNotifier`、`ListenableBuilder`、构造器注入和 `Navigator` 学会原理；遇到真实复杂度后再判断是否需要第三方状态管理或路由包。

建议目录会随着阶段逐步创建，而不是第一天一次性搭空架子：

```text
lib/
├── app/             App、主题、导航壳、依赖组装
├── core/            通用错误、时间与小型工具
├── domain/          领域模型与纯业务规则
├── application/     业务工作流
├── data/            数据库、仓库、文件、通知
└── features/        按 Goal / Mission / Evidence 等功能组织 UI
```

## 5. 分阶段路线

### 阶段 0：建立可验证的开发基线

**学习重点**：Flutter 工程结构、热重载与完整重启的区别、静态检查、测试、Git 小步提交。

任务：

- 确认 Windows 与 Android 设备均能识别。
- 运行当前 Hello World。
- 建立统一的日常检查命令。
- 增加第一个最小 Widget Test，确认测试链路有效。
- 记录模拟器或真机、窗口尺寸和调试方式。

验收：

```powershell
dart format --output=none --set-exit-if-changed lib test
flutter analyze --no-pub
flutter test --no-pub
flutter run -d windows
flutter run -d <android-device-id>
```

阶段产物：一个没有业务功能但在两端可运行、可检查、可测试的干净基线。

### 阶段 1：应用外壳与视觉语言

**学习重点**：`MaterialApp`、Theme、页面拆分、底部导航、`IndexedStack`、响应式约束、可复用 Widget。

任务：

- 建立 `MissionBookApp` 和暖白 / 深绿的主题 token。
- 建立 Today、Goals、History、Me 四个空状态页面。
- 使用底部导航切换顶层页面并保持各页状态。
- 实现统一的页面背景、标题、卡片和底部通栏主按钮。
- 在窄屏、键盘弹出和 Windows 宽窗口下检查布局。

验收：四个顶层页面可切换；没有业务假数据；Android 常见窄屏无 overflow。

### 阶段 2：页面导航与表单基础

**学习重点**：`Navigator.push/pop`、路由栈、`Form`、`GlobalKey<FormState>`、输入校验、异步提交状态。

任务：

- 从 Goals 进入“新建目标”表单。
- 完成标题、说明、Why 的输入与校验。
- 先通过内存中的临时 Store 保存，用于学习完整 UI 数据流。
- 实现提交中、提交失败、提交成功返回三种反馈。
- 编写表单校验与页面跳转测试。

验收：可以创建一个临时 Goal 并在 Goals 列表看到；重启后消失是此阶段的已知限制。

### 阶段 3：领域模型与纯业务规则

**学习重点**：Dart class、enum、不可变对象、nullable、`copyWith`、纯函数、单元测试。

任务：

- 实现当前版本真正需要的枚举和值对象。
- 建立 Goal、GoalNode、Mission、ScheduleRevision、ExecutionPlan、ExecutionEvent、Evidence、FailureRecord。
- 实现 ExecutionEvent 的合法序列检查。
- 实现 Elapsed / Paused / Focus / Overtime 的纯计算函数。
- 实现 VerificationPolicy 的结果矩阵。

验收：领域层不依赖 Flutter；正常、暂停、跨暂停结束、延长和非法事件序列均有单元测试。

### 阶段 4：Drift 数据库与 Repository

**学习重点**：SQLite 表、主键外键、Drift、Stream 查询、Repository、UTC 与本地时间、事务。

任务：

- 建立规格规定的八张表，`schemaVersion = 1`。
- 启用外键并为稳定字符串枚举建立安全映射。
- 建立数据库与领域对象之间的转换。
- 实现 Goal Repository 的增改查。
- 用真实数据库替换阶段 2 的内存 Store。
- 增加关闭数据库后重开的持久化测试。

验收：创建 Goal 后重启应用仍存在；未知枚举与损坏关系明确失败，不静默猜测。

### 阶段 5：Goal 与 GoalNode 完整切片

**学习重点**：树结构、递归 Widget、有序数据、编辑状态、派生展示。

任务：

- Goals 列表：Active / Paused / Achieved 分类与明确空状态。
- Goal Detail：树形展示 GoalNode。
- 新增根节点、添加子节点、改名、删除、同级调序。
- Goal 编辑与状态变更。
- 用关联 Mission 的真实记录展示节点完成情况，不使用“掌握度”。

验收：多层节点的父子关系、描述和顺序在重启后保持；跨 Goal 的父子关系会被拒绝。

### 阶段 6：Goal Outline JSON 导入

**学习重点**：JSON 解码、递归校验、sealed result、预览与确认、批量事务、文件选择。

任务：

- 实现协议解析器与明确的错误信息。
- 校验 schema、version、必填字段、key 唯一性以及 2 MB / 12 层 / 500 节点上限。
- 支持粘贴文本 → 校验 → Tree Preview → 确认。
- 支持 Windows 与 Android 系统文件选择器。
- 确认后用一次事务写入 Goal 与 GoalNode。

验收：非法 JSON 不写入；预览前不写入；任意节点写入失败不留下半个 Goal。

### 阶段 7：Mission 创建完整切片

**学习重点**：较长表单拆分、条件字段、日期时间输入、跨对象原子保存。

任务：

- 支持独立 Mission，以及从 GoalNode 进入创建。
- 输入 Title / Why / What / How / Verify。
- 输入日期、计划时长、FIXED / FLEXIBLE 与 VerificationPolicy。
- REQUIRED_EVIDENCE 时要求 Evidence Deadline。
- 从 GoalNode 预填标题、说明和 Goal Why，但不编造 Steps / Verify。
- `CreateMission` 在一个事务中保存 Mission、ExecutionPlan、ScheduleRevision。

验收：保存成功后三部分同时存在并出现在对应日期；任何失败都不留半条链。

### 阶段 8：Today 与 Mission Detail

**学习重点**：数据库响应式查询、日期分组、列表状态、组合展示、页面间数据刷新。

任务：

- Today 查询当天 Mission，并展示当前 Mission、列表和完成记录。
- Mission Detail 组合展示 Why / What / How / Verify。
- 处理 Scheduled / Ready / Running / Paused / Evidence Pending 等真实按钮状态。
- 只允许 START 前编辑 ExecutionPlan。
- 实现加载、空数据、失败与重试界面。

验收：页面完全来自规范化本地数据；不读取导入 Raw JSON；不显示模拟内容。

### 阶段 9：Mission 执行状态机

**学习重点**：状态机、应用工作流、事务、基于事件的计时、生命周期恢复。

任务：

- 实现 Start / Pause / Resume / Extend / End 工作流。
- 每个操作先校验状态，再在事务中写事件与当前状态投影。
- In Mission 页面按事件实时计算 Elapsed 与 Focus。
- 到达原计划 Focus 时长时提示结束或继续，不自动完成。
- End 区分 COMPLETED / NOT_COMPLETED。
- 未完成时保存可选 FailureRecord。

验收：非法转换被拒绝；暂停时间不计入 Focus；延长不改写原计划时长；关闭并重启后计时正确。

### 阶段 10：重启恢复与 Deadline

**学习重点**：异步启动、Bootstrap、恢复中的 UI、数据库事实与页面投影、时间边界测试。

任务：

- 启动时恢复 Running、Paused、Evidence Pending、Evaluation Pending。
- 根据事件重建或校验执行状态投影。
- 补算错过的 Required Evidence Deadline。
- Deadline 超时原子写入 VerificationState、ClosureReason 与 FailureRecord。
- 实现初始化失败、重试与不可恢复数据错误提示。

验收：在 Running 和 Paused 两种状态分别杀进程重启，Focus 均正确；Deadline 不会把 COMPLETED 改写成 NOT_COMPLETED。

### 阶段 11：Evidence 与 Result

**学习重点**：页面局部草稿状态、文件复制、应用私有目录、Finalize 边界、图片预览。

任务：

- Evidence Draft 支持文字、代码、图片、文件、手动记录。
- Draft 可自由增删改，并明确“尚未进入正式历史”。
- 附件限制 20 MB，复制到应用私有目录，只保存相对 storageKey。
- Finalize 时一次事务写 Formal Evidence 并进入 Evaluation Pending。
- Result 展示执行事实、证据和“智能评价暂未接入”。
- 用户确认后以 `EVALUATION_NOT_AVAILABLE` 关闭。

验收：Finalize 前数据库无 Formal Evidence；Finalize 后重启仍可读取附件；不出现模拟评分或 AI 评语。

### 阶段 12：History、统计与 Goal 完成记录

**学习重点**：聚合查询、派生数据、日期边界、网格布局、性能意识。

任务：

- History 按时间倒序展示 Mission、日期、Focus 和结果。
- Today 展示最近 7 天计划 / 完成情况与近 30 天完成格子。
- 完成数严格来自真实 END 事件。
- Goal / GoalNode 汇总关联 Mission 的完成记录。
- Me 提供数据导出入口、设置与关于的最小界面。

验收：跨日期、无数据、只有未完成、跨暂停的记录均正确；页面不用“掌握”措辞。

### 阶段 13：本地通知

**学习重点**：平台权限、系统通知与数据库状态对账、平台通道、失败降级。

任务：

- FIXED Mission 的到点提醒；FLEXIBLE 不安排开始提醒。
- 提供开始与延后 15 分钟；延后不写 START Event。
- Running / Paused 执行通知与状态同步。
- “停止”先 Pause，再进入结束确认。
- 启动时以数据库事实重新对账通知。
- 处理 Android 通知 / 精确闹钟权限与 Windows Toast 限制。

验收：拒绝权限不回滚业务数据；通知操作最多产生一条对应事件；重启后通知与状态一致。

### 阶段 14：双端收尾与发布候选

**学习重点**：集成测试思维、真实设备调试、错误日志、构建产物、回归检查。

任务：

- 完成所有领域、Workflow、数据库和关键 Widget 测试。
- 在 Windows 与 Android 分别走完整自用验收链路。
- 检查窄屏、键盘、系统返回、深层树、大纲上限和附件错误。
- 检查品牌图标、中文文案、空状态与错误提示。
- 构建 Windows 与 Android release 候选。

验收：两端均完成“创建 → 执行一半 → 重启 → 恢复 → Evidence → Result → 再次重启查看历史”的真实链路。

## 6. 每阶段统一质量门槛

进入下一阶段前必须同时满足：

- 能说明本阶段的数据流和关键设计理由。
- 新增代码已格式化，`flutter analyze` 无问题。
- 纯业务规则有单元测试，关键页面交互有 Widget Test。
- 手工验收路径走通。
- 没有引入规格明确排除的未来功能。
- 没有用示例数据、模拟评价或内存状态掩盖持久化问题。
- Git 工作区中的本阶段改动可以用一句话准确描述。

## 8. 第一个任务

从 **0.1 认识并验证当前工程** 开始，不立即改架构：

1. 读懂 `lib/main.dart` 中 `main → runApp → MaterialApp → Scaffold` 的构建关系。
2. 在 Windows 运行当前页面，并亲手修改标题验证 Hot Reload。
3. 恢复标题后执行格式化、静态检查和测试。
4. 确认一个 Android 设备可运行当前页面。
5. 由我们共同总结 Hot Reload、Hot Restart 和应用完整重启分别保留什么。

0.1 验收后再领取 0.2，不跨阶段并行堆功能。
